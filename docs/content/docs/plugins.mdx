title: Plugins
description: Add endpoints and helpers to your API, fully typed in your handlers, on any adapter.

A plugin adds endpoints, helpers your handlers can call, or both. It gets your api, and everything it adds is typed.

## Installing one

Plugins go under `plugins` on [`defineConfig`](/docs/reference/define-config), as a list:

```ts title="kizuna.config.ts"
import { defineConfig } from '@ts-kizuna/core';
import { expressAdapter } from '@ts-kizuna/express';
import { mcpPlugin } from '@ts-kizuna/mcp';
import { routes } from './src/routes';

export default defineConfig({
    adapter: expressAdapter(),
    routes,
    plugins: [
        mcpPlugin({
            name: 'My API',
        }),
    ],
});
```

`api.mount` then serves its routes along with yours, on every adapter.

## Slugs

Each plugin carries a slug, which is the key it installs at and what handlers reach it under. Every plugin defaults its own, so a list is all you write.

Installing two of the same plugin is where you override one:

```ts title="kizuna.config.ts"
plugins: [
    mcpPlugin({
        name: 'My API',
    }),
    mcpPlugin({
        slug: 'internalMcp',
        path: '/internal/mcp',
        name: 'My API, internal',
    }),
],
```

Handlers then read the first under `plugins.mcp` and the second under `plugins.internalMcp`.

## Using what a plugin offers

A plugin can hand your handlers functions to call, under `plugins`:

```ts title="src/routes/users.ts"
updateUser: k
    .route({
        method: 'PATCH',
        path: '/users/:id',
        body: UpdateUserSchema,
        responses: {
            200: UserSchema,
        },
    })
    .handler(async ({ params, body, plugins }) => {
        const user = await db.users.update(params.id, body);
        plugins.audit.record('users.updateUser');

        return {
            status: 200,
            body: user,
        };
    }),
```

Plugin slugs come from other people, so they are namespaced under `plugins` rather than spread into the handler args, where one called `body` would shadow your request body. Destructure it for the short form:

```ts
.handler(async ({ params, body, plugins: { audit } }) => {
```

A config with no plugins gets no `plugins` argument at all.

## Plugin routes

A plugin's routes run through the same pipeline as yours, with the same validation, guards, access control and problem details. They never join `api.routes`, so they stay out of everything generated from it.

|                           | your routes | a plugin's routes |
| ------------------------- | ----------- | ----------------- |
| declared with             | `k.routes`  | the plugin        |
| served by `api.mount`     | yes         | yes               |
| validated, guarded        | yes         | yes               |
| in your fetch client      | yes         | **no**            |
| in OpenAPI, Swift, Kotlin | yes         | **no**            |

If a plugin claims a path your routes already use, `defineConfig` throws and names both.

## What a plugin sees

A plugin is handed the api when it starts serving, so it can read every route, tag, identity and schema you declared. That is how [`mcpPlugin`](/docs/reference/mcp-plugin) knows which routes say `tool`, and how [`openApiPlugin`](/docs/reference/openapi-plugin) builds a document without being told what is in your API.

Your config stays a list of plugins, with no routes to pass across.

## Where a plugin runs

A plugin's `serve` runs on the server, beside your handlers, so it may import anything they may: Node built-ins, a database driver, an SDK. Your config is server-side too, and a browser imports the client [`kizuna generate`](/docs/configuration) writes rather than the config itself.
