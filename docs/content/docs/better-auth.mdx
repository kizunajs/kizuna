[Better Auth](https://better-auth.com) often runs as its own app, next to your API. `@kizunajs/better-auth` lets your API own every user flow while Better Auth does the work. Your routes call any Better Auth endpoint, typed, and everything Better Auth sends, from password reset emails to "a user signed up", comes back to your API.

That gets you:

- **Every Better Auth endpoint in your handlers**, typed, including the ones its plugins add, like organizations.
- **Every event in your API**, typed from your Better Auth app's own type: its core callbacks, what happens to its users, and the callbacks of any plugin, SSO and your own included.
- **One API for your apps.** "Change my email" is a route of your own, so it's in your OpenAPI document and your Swift, Kotlin and fetch clients.
- **Nothing to keep up with.** A plugin you add to Better Auth, or a callback Better Auth adds in an upgrade, reaches your API typed without a change to this package.

Changing an email shows the whole loop:

1. Your app calls your route, `PATCH /account/email`.
2. The route calls `plugins.betterAuth.changeEmail`, passing on the user's credential.
3. Better Auth creates the token and calls `sendChangeEmailConfirmation`, which comes back to your API as `user.changeEmail.sendChangeEmailConfirmation`.
4. Your function sends the email with `plugins.resend`.

<Step>

### Create the client and the plugin

Create Better Auth's client for your Better Auth app, and build the plugin around it. Add a client plugin for each Better Auth plugin your app runs, the way Better Auth's own [client docs](https://better-auth.com/docs/concepts/client) describe, and its endpoints are typed too. `app` names your Better Auth app's type, so every event it sends is typed:

```ts title="src/better-auth.ts"
import { createAuthClient } from 'better-auth/client';
import { organizationClient } from 'better-auth/client/plugins';
import { betterAuthApp, defineBetterAuthPlugin } from '@kizunajs/better-auth';
import type { auth } from '../../auth/src/auth';

export const authClient = createAuthClient({
    baseURL: 'https://auth.example.com',
    plugins: [organizationClient()],
});

export const betterAuthPlugin = defineBetterAuthPlugin({
    client: authClient,
    app: betterAuthApp<typeof auth>(),
});
```

`import type` brings in the type alone, so none of the Better Auth app runs in your API. When the Better Auth app lives in another repository, leave `app` out, see [Without the app's type](#without-the-apps-type).

Keep it in a module of its own. `kizuna generate` types `plugins.betterAuth` and every event from `betterAuthPlugin`, so it needs a name to import.

</Step>

<Step>

### Know who's calling

An identity whose guard asks Better Auth for the session. Better Auth checks the token, and the guard hands your handlers the user:

```ts title="src/identities.ts"
import { authClient } from './better-auth';

export const member = k.identity
    .bearer({
        context: z.object({
            userId: z.string(),
            token: z.string(),
        }),
    })
    .guard(async ({ bearer, deny }) => {
        if (bearer === null) {
            return deny({
                status: 401,
                body: {
                    detail: 'Sign in first',
                },
            });
        }

        const { data } = await authClient.getSession({
            fetchOptions: {
                headers: {
                    authorization: `Bearer ${bearer.token}`,
                },
            },
        });
        if (data === null) {
            return deny({
                status: 401,
                body: {
                    detail: 'Sign in first',
                },
            });
        }

        return {
            userId: data.user.id,
            token: bearer.token,
        };
    });
```

The token rides along in the context, so routes can pass it on to Better Auth. The Better Auth app needs its [`bearer`](https://better-auth.com/docs/plugins/bearer) plugin to accept it. For browsers that sign in with cookies, see [Passing the user's credential](#passing-the-users-credential).

</Step>

<Step>

### Write what each event does

Write the functions in a file of their own with `defineBetterAuthEvents`. Give it your `Config`, the way you give it to `new Kizuna<Config>()`, and every event, `jobs` and `plugins` are typed from your app. An event is named by where its callback sits in Better Auth's options:

```ts title="src/better-auth-events.ts"
import { defineBetterAuthEvents } from '@kizunajs/better-auth';
import type { Config } from '../kizuna.types';

export const betterAuthEvents = defineBetterAuthEvents<Config>({
    'user.changeEmail.sendChangeEmailConfirmation': async ({ data, plugins }) => {
        await plugins.resend.sendEmail({
            to: data.user.email,
            subject: 'Confirm your new email',
            html: `<p>Change your email to ${data.newEmail}?</p><a href="${data.url}">Confirm</a>`,
        });
    },
    'emailAndPassword.sendResetPassword': async ({ data, plugins }) => {
        await plugins.resend.sendEmail({
            to: data.user.email,
            subject: 'Reset your password',
            html: `<a href="${data.url}">Reset your password</a>`,
        });
    },
});
```

Your editor lists every event your Better Auth app can send, so there's no name to look up.

</Step>

<Step>

### Install the plugin

The route Better Auth sends its events to needs a caller too, so `auth` names the identity your Better Auth app signs in as, like a service token:

```ts title="kizuna.config.ts"
import { betterAuthPlugin } from './src/better-auth';
import { betterAuthEvents } from './src/better-auth-events';

export default defineConfig({
    adapter: expressAdapter(),
    routes,
    auth: {
        identities: {
            member,
            service,
        },
    },
    plugins: [
        resendPlugin({
            apiKey: process.env.RESEND_API_KEY,
            from: 'Kizuna <hello@example.com>',
        }),
        betterAuthPlugin({
            auth: 'service',
            on: betterAuthEvents,
        }),
    ],
});
```

That serves `POST /better-auth/webhooks` for Better Auth's events. A call without the identity is answered by its guard, and nothing runs. `auth: false` stops the app at startup, since an open route would let anyone send your emails.

</Step>

</Steps>

## In your Better Auth app

<InstallTabs packageName="@kizunajs/better-auth" />

Create the `kizuna` plugin, add it to Better Auth's plugins, and place `forward()` in the callbacks other plugins take:

```ts title="auth.ts"
import { betterAuth } from 'better-auth';
import { bearer, magicLink, organization } from 'better-auth/plugins';
import { kizuna } from '@kizunajs/better-auth/client';

const kizunaApi = kizuna({
    url: 'https://api.example.com/better-auth/webhooks',
    headers: {
        authorization: `Bearer ${process.env.KIZUNA_SERVICE_TOKEN}`,
    },
});

export const auth = betterAuth({
    emailAndPassword: {
        enabled: true,
    },
    plugins: [
        bearer(),
        magicLink({
            sendMagicLink: kizunaApi.forward(),
        }),
        organization({
            sendInvitationEmail: kizunaApi.forward(),
        }),
        kizunaApi,
    ],
});
```

**The core fills itself.** `kizuna` fills Better Auth's own callbacks and hooks: password resets, email verification, changing email, deleting accounts, and when a user is created, updated or deleted, verifies their email, resets their password or signs in. It turns on changing email and deleting accounts, since your API starts those. Anything you set yourself wins, `enabled: false` included.

**`forward()` does the rest.** A plugin takes its callbacks when you create it, so `forward()` goes wherever a plugin wants one: magic links, one-time codes, phone numbers, two-factor, SSO, or a plugin of your own. It needs no name. When Better Auth starts, `kizuna` finds each `forward()` and names it by where it sits, like `magic-link.sendMagicLink`, and that's the event your API receives. Its type comes from the option it's placed in, and it only fits a callback that reports something: an option that has to return a value, like `generateToken`, is a type error.

When the credential changes, like a token that expires, pass `headers` as a function, and it runs before every event.

`@kizunajs/better-auth/client` never imports `kizunajs`, so the Better Auth app installs nothing from your API.

## What your routes can do

`plugins.betterAuth` is your Better Auth client, so a route calls whatever Better Auth offers, passing on the user's credential in `fetchOptions`. The examples use this helper:

```ts title="src/better-auth.ts"
export const asUser = (token: string) => ({
    fetchOptions: {
        headers: {
            authorization: `Bearer ${token}`,
        },
    },
});
```

### Change an email

```ts title="src/routes/account.ts"
changeEmail: k
    .route({
        method: 'PATCH',
        path: '/account/email',
        auth: 'member',
        body: z.object({
            email: z.email(),
        }),
        responses: {
            204: z.void(),
        },
    })
    .handler(async ({ auth, body, plugins }) => {
        await plugins.betterAuth.changeEmail({
            newEmail: body.email,
            ...asUser(auth.member.token),
        });

        return {
            status: 204,
            body: undefined,
        };
    }),
```

A verified user confirms from their current address through `user.changeEmail.sendChangeEmailConfirmation`, before Better Auth verifies the new one.

### Reset a password

Two routes that need no sign-in. The first emails the link through `emailAndPassword.sendResetPassword`, and the second sets the password with the token from it:

```ts title="src/routes/account.ts"
requestPasswordReset: k
    .route({
        method: 'POST',
        path: '/account/password-reset',
        auth: false,
        body: z.object({
            email: z.email(),
        }),
        responses: {
            204: z.void(),
        },
    })
    .handler(async ({ body, plugins }) => {
        await plugins.betterAuth.requestPasswordReset({
            email: body.email,
            redirectTo: 'https://app.example.com/reset-password',
        });

        return {
            status: 204,
            body: undefined,
        };
    }),
resetPassword: k
    .route({
        method: 'PUT',
        path: '/account/password',
        auth: false,
        body: z.object({
            token: z.string(),
            newPassword: z.string(),
        }),
        responses: {
            204: z.void(),
        },
    })
    .handler(async ({ body, plugins }) => {
        await plugins.betterAuth.resetPassword(body);

        return {
            status: 204,
            body: undefined,
        };
    }),
```

`redirectTo` has to be one of Better Auth's `trustedOrigins`.

### Delete an account

```ts title="src/routes/account.ts"
.handler(async ({ auth, plugins }) => {
    await plugins.betterAuth.deleteUser(asUser(auth.member.token));

    return {
        status: 204,
        body: undefined,
    };
}),
```

The account is deleted when the user follows the link `user.deleteUser.sendDeleteAccountVerification` sent, not before. To keep that step in your API too, send your own link with the `token`, and let a route pass it back:

```ts title="src/routes/account.ts"
await plugins.betterAuth.deleteUser({
    token: body.token,
    ...asUser(auth.member.token),
});
```

### Invite to an organization

Every endpoint a Better Auth plugin adds is there too, typed once its client plugin is on your client:

```ts title="src/routes/organizations.ts"
invite: k
    .route({
        method: 'POST',
        path: '/organizations/:organizationId/invitations',
        auth: 'member',
        body: z.object({
            email: z.email(),
        }),
        responses: {
            204: z.void(),
        },
    })
    .handler(async ({ auth, params, body, plugins }) => {
        await plugins.betterAuth.organization.inviteMember({
            organizationId: params.organizationId,
            email: body.email,
            role: 'member',
            ...asUser(auth.member.token),
        });

        return {
            status: 204,
            body: undefined,
        };
    }),
```

The invitation email comes back as `organization.sendInvitationEmail`.

### Sign in with a magic link or a code

With the magic link and email OTP plugins on your client, sign-in starts at your routes too, and the email goes out from your API:

```ts title="src/routes/sign-in.ts"
sendMagicLink: k
    .route({
        method: 'POST',
        path: '/sign-in/magic-link',
        auth: false,
        body: z.object({
            email: z.email(),
        }),
        responses: {
            204: z.void(),
        },
    })
    .handler(async ({ body, plugins }) => {
        await plugins.betterAuth.signIn.magicLink({
            email: body.email,
        });

        return {
            status: 204,
            body: undefined,
        };
    }),
```

A code works the same way through `plugins.betterAuth.emailOtp.sendVerificationOtp({ email, type: 'sign-in' })`, and arrives as `email-otp.sendVerificationOTP`.

### Anything else Better Auth does

A "signed-in devices" screen is two routes over Better Auth's session endpoints:

```ts title="src/routes/account.ts"
.handler(async ({ auth, plugins }) => {
    const { data } = await plugins.betterAuth.listSessions(asUser(auth.member.token));

    return {
        status: 200,
        body: (data ?? []).map((session) => ({
            id: session.id,
            userAgent: session.userAgent ?? null,
        })),
    };
}),
```

`plugins.betterAuth.revokeSession` signs one of them out. Whatever plugins your Better Auth app runs, your routes can call, once their client plugin is on your client.

### Better Auth's errors

Better Auth's client answers with `{ data, error }` instead of throwing. Turn an `error` into one of your route's declared responses, here a `422`:

```ts title="src/routes/account.ts"
const { error } = await plugins.betterAuth.changeEmail({
    newEmail: body.email,
    ...asUser(auth.member.token),
});
if (error) {
    return throwError({
        status: 422,
        body: {
            detail: error.message ?? 'The email could not be changed.',
        },
    });
}
```

## React to what users do

Better Auth tells your API what happened, after it has happened, so your API keeps its own data in step. Create a profile and queue the welcome email when someone signs up:

```ts title="src/better-auth-events.ts"
export const betterAuthEvents = defineBetterAuthEvents<Config>({
    'databaseHooks.user.create.after': async ({ data, jobs }) => {
        await db.profiles.create({
            userId: data.id,
            displayName: data.name,
        });

        await jobs.users.sendWelcomeEmail.queue({
            input: {
                userId: data.id,
            },
        });
    },
    'databaseHooks.user.delete.after': async ({ data }) => {
        await db.profiles.delete(data.id);
    },
});
```

`databaseHooks.session.create.after` arrives on each sign-in, with the session's `ipAddress` and `userAgent`, for a "new sign-in to your account" email. Its token stays with Better Auth.

A delivery your API doesn't take is logged in the Better Auth app and not sent again, and the user's sign-up or sign-in goes through as usual. If you set your own `afterEmailVerification` or `onPasswordReset`, yours wins and that event stays in the Better Auth app, so move that work into your API's function instead.

## Passing the user's credential

Better Auth checks every call against the credential it carries, so a route passes on the one its user sent.

- **A bearer token**, the way the Swift and Kotlin clients send it, goes in `authorization`. The Better Auth app runs its `bearer` plugin.
- **A browser's cookie** goes in `cookie`, together with the request's `origin`. Better Auth refuses a call that carries a cookie unless its `origin` is one of its `trustedOrigins`, so pass the browser's own:

    ```ts
    fetchOptions: {
        headers: {
            cookie: headers.cookie,
            origin: headers.origin,
        },
    },
    ```

Better Auth rate-limits by IP address, and every call from your API arrives from the API's address. See Better Auth's [`advanced.ipAddress`](https://better-auth.com/docs/reference/options) options for passing the user's address along.

## The events

Each function receives:

| Argument  | What it is                                                  |
| --------- | ----------------------------------------------------------- |
| `event`   | The event's name, like `emailAndPassword.sendResetPassword` |
| `data`    | What Better Auth handed the callback, as JSON               |
| `jobs`    | Your app's jobs, to queue work                              |
| `plugins` | Your installed plugins, `plugins.betterAuth` included       |

An event is named by where its callback sits in Better Auth's options. `kizuna` fills these core ones:

| Event                                           | When                                        | `data`                             |
| ----------------------------------------------- | ------------------------------------------- | ---------------------------------- |
| `emailAndPassword.sendResetPassword`            | Someone asks for a password reset           | `user`, `url`, `token`             |
| `emailVerification.sendVerificationEmail`       | A user needs to verify their email          | `user`, `url`, `token`             |
| `user.changeEmail.sendChangeEmailConfirmation`  | A verified user asks to change their email  | `user`, `newEmail`, `url`, `token` |
| `user.deleteUser.sendDeleteAccountVerification` | A user asks to delete their account         | `user`, `url`, `token`             |
| `databaseHooks.user.create.after`               | Someone signed up                           | the user                           |
| `databaseHooks.user.update.after`               | A user changed, like their name             | the user                           |
| `databaseHooks.user.delete.after`               | A user was deleted                          | the user                           |
| `emailVerification.afterEmailVerification`      | A user verified their email                 | the user                           |
| `emailAndPassword.onPasswordReset`              | A user set a new password from a reset link | `user`                             |
| `databaseHooks.session.create.after`            | A user signed in                            | the session, without its token     |

A plugin's event is its id and the path of its `forward()`, like `magic-link.sendMagicLink`, `organization.sendInvitationEmail`, `email-otp.sendVerificationOTP` or `two-factor.otpOptions.sendOTP`, with `data` as that plugin hands it over.

`data` is typed from your Better Auth app's own type, so a field Better Auth adds reaches your functions typed when you upgrade. It travels as JSON: dates arrive as ISO strings, and anything JSON can't carry, like functions, is left out. Better Auth's `request` argument is never sent. The route checks that the body is an event, and one with no function is acknowledged and dropped.

### Your own user fields

`data.user`, and the user record the hooks hand over, carry your `additionalFields`, typed from your Better Auth app's config:

```ts title="src/better-auth-events.ts"
export const betterAuthEvents = defineBetterAuthEvents<Config>({
    'emailVerification.sendVerificationEmail': async ({ data, plugins }) => {
        await plugins.resend.sendEmail({
            to: data.user.email,
            subject: data.user.plan === 'pro' ? 'Welcome to Pro' : 'Verify your email',
            html: `<a href="${data.url}">Verify your email</a>`,
        });
    },
});
```

A date field is a `string`, since that's how it arrives.

### Without the app's type

When the Better Auth app lives in another repository, the API can't import its type, so leave `app` out. The core events stay typed from Better Auth itself. The events of its plugins still arrive, at `'*'`, with `data` as a record:

```ts title="src/better-auth-events.ts"
export const betterAuthEvents = defineBetterAuthEvents<Config>({
    '*': async ({ event, data, plugins }) => {
        if (event === 'magic-link.sendMagicLink') {
            await plugins.resend.sendEmail({
                to: String(data.email),
                subject: 'Your sign-in link',
                html: `<a href="${String(data.url)}">Sign in</a>`,
            });
        }
    },
});
```

Your own user fields come from your client then: add them with Better Auth's `inferAdditionalFields` client plugin.

### When an event fails

An email event your API doesn't answer with `2xx` throws in the Better Auth app, naming the event and the status. Better Auth logs what a callback throws and answers the request as usual, so a user asking for a password reset never learns whether the email went out. Watch the Better Auth app's logs.

Better Auth waits for the callback before it answers, so keep your functions quick. For anything slow, queue a [job](/docs/jobs) and return.

## Moving the route

The plugin serves its events route under `/better-auth`. When that clashes with your own routes, pass another base path, and point the Better Auth app at it:

```ts title="kizuna.config.ts"
betterAuthPlugin({
    auth: 'service',
    on: betterAuthEvents,
    basePath: '/integrations/better-auth',
}),
```

The route is [hidden](/docs/routes#hidden-routes), so it stays out of your clients and the OpenAPI document.

## Options

`defineBetterAuthPlugin`:

| Option   | Default  | Description                                                                                 |
| -------- | -------- | ------------------------------------------------------------------------------------------- |
| `client` | required | Your Better Auth client, from `createAuthClient`. Handlers reach it at `plugins.betterAuth` |
| `app`    | none     | Your Better Auth app's type, as `betterAuthApp<typeof auth>()`, so every event is typed     |

The plugin it returns:

| Option     | Default        | Description                                                              |
| ---------- | -------------- | ------------------------------------------------------------------------ |
| `auth`     | required       | The identity the Better Auth app calls with, written as a route's `auth` |
| `on`       | required       | A function per event, built with `defineBetterAuthEvents`                |
| `basePath` | `/better-auth` | Where the events route is served                                         |

`kizuna`:

| Option    | Default  | Description                                                                      |
| --------- | -------- | -------------------------------------------------------------------------------- |
| `url`     | required | The events route's full URL, like `https://api.example.com/better-auth/webhooks` |
| `headers` | none     | Sent with every event, or a function that returns them before each one           |
