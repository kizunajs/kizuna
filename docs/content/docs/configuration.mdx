title: Configuration

---

`kizuna.config.ts` sits at the root of your app, beside `package.json`. It assembles everything the API is made of, hands back the `api` you mount, and says where each generated client is written. The tooling looks for it by name.

## The file

```ts title="kizuna.config.ts"
import { defineConfig } from '@ts-kizuna/core';
import { expressAdapter } from '@ts-kizuna/express';
import { swiftClient } from '@ts-kizuna/swift';
import { routes } from './src/routes';
import { user } from './src/identities';

export default defineConfig({
    adapter: expressAdapter(),
    routes,
    auth: {
        identities: {
            user,
        },
    },
    clients: [
        swiftClient({
            output: './ios/MyApp/Generated/APIClient.swift',
            namespace: 'API',
        }),
    ],
});
```

It default-exports two things: `api`, which you mount and which every generator reads, and `clients`, which the CLI writes.

```ts title="src/index.ts"
import kizuna from '../kizuna.config';

kizuna.api.mount(app);
```

See [`defineConfig`](/docs/reference/define-config) for every field it takes.

## Clients

Each client comes from the package that generates it, so its options are typed there and a generator you have not installed cannot be configured by accident.

| Target            | Import from          | Writes                        |
| ----------------- | -------------------- | ----------------------------- |
| `fetchClient`     | `@ts-kizuna/fetch`   | A typed TypeScript client     |
| `swiftClient`     | `@ts-kizuna/swift`   | A native Swift client         |
| `kotlinClient`    | `@ts-kizuna/kotlin`  | A native Kotlin client        |
| `openApiDocument` | `@ts-kizuna/openapi` | The OpenAPI document, to disk |

```ts title="kizuna.config.ts"
clients: [
    fetchClient({
        output: './packages/api-client/src/generated.ts',
    }),
    openApiDocument({
        output: './openapi.yaml',
    }),
],
```

Your config carries the handlers, so it stays on the server. A browser imports the generated client, which holds the route shapes and the schemas and nothing a handler reached for.

## Client options

| Option                | Applies to    | Description                                                               |
| --------------------- | ------------- | ------------------------------------------------------------------------- |
| `output`              | all           | Path the generated file is written to                                     |
| `namespace`           | Swift, Kotlin | Name of the generated namespace, `API` by default                         |
| `package`             | Kotlin        | Package the generated file declares                                       |
| `camelCaseProperties` | Swift, Kotlin | Convert wire field names to camelCase, mapping the wire name back         |
| `unknownEnumCase`     | Swift, Kotlin | Give every enum an `unknown` case, so an unrecognised value still decodes |

`openApiDocument` takes the same overrides [`generateOpenApi`](/docs/reference/generate-openapi) does, and picks its format from the output extension: `.json` renders JSON, anything else renders YAML.

## Two clients of one language

Add two entries.

```ts title="kizuna.config.ts"
clients: [
    swiftClient({
        output: './ios/MyApp/Generated/APIClient.swift',
        namespace: 'API',
    }),
    swiftClient({
        output: './ios/MyApp/Generated/OpenEnumAPIClient.swift',
        namespace: 'OpenEnumAPI',
        unknownEnumCase: true,
    }),
],
```

## More than one API

A repository serving several APIs writes a config file for each, and each keeps its own routes and its own generated clients:

```
my-repo/
├── kizuna.config.ts
└── kizuna.workspace.config.ts
```

Point a generator at the one you mean with its `--config` flag, suffixing an export when the file holds more than the default:

```sh title="Terminal"
ts-kizuna-swift generate --config kizuna.workspace.config.ts --output ... --namespace-name WorkspaceAPI
```

## `kizuna generate`

<InstallTabs packageName="-D @ts-kizuna/cli" />

```sh title="Terminal"
kizuna generate
```

It writes two things from `kizuna.config.ts`: the `Config` in `kizuna.types.ts`, and every client under `clients`. A file that already matches is left alone, so watchers and build tools see no change.

| Option     | Default            | Description                                                                             |
| ---------- | ------------------ | --------------------------------------------------------------------------------------- |
| `--check`  | off                | Report what would be rewritten and write nothing. See [below](#kizuna-generate---check) |
| `--config` | `kizuna.config.ts` | The config to read                                                                      |
| `--types`  | the config's own   | Where the `Config` is written, overriding `typescript.outputFile`                       |

Where the types land is usually the config's business rather than the command's:

```ts title="kizuna.config.ts"
export default defineConfig({
    adapter: expressAdapter(),
    routes,
    typescript: {
        outputFile: './src/kizuna.types.ts',
    },
});
```

Add it to your `package.json` and run it after changing the config:

```json title="package.json"
{
    "scripts": {
        "kizuna:generate": "kizuna generate",
        "kizuna:check": "kizuna generate --check"
    }
}
```

### `kizuna.types.ts`

The `Config` interface is read from your config's syntax, not by running it. That is what lets `k` be typed by the config that serves your routes without the routes waiting on a config that loads.

```ts title="kizuna.types.ts"
/**
 * This file was automatically generated by ts-kizuna.
 * DO NOT MODIFY IT BY HAND. Instead, modify your source kizuna config,
 * and re-run `kizuna generate` to regenerate this file.
 */
import type { expressAdapter } from '@ts-kizuna/express';
import type { tags, user } from '@my-repo/api';

export interface Config {
    adapter: ReturnType<typeof expressAdapter>;
    tags: typeof tags;
    auth: {
        identities: {
            user: typeof user;
        };
    };
}
```

It carries `adapter`, `tags`, `auth`, `requestContext`, `validation`, `jobs` and `plugins`. Your `routes` stay out: they are read at runtime, and typing against them would make the config a prerequisite for declaring the routes it serves.

Point `new Kizuna<Config>()` at it once and every name you write is checked against it:

```ts title="src/k.ts"
import { Kizuna } from '@ts-kizuna/core';
import type { Config } from '../kizuna.types';

export const k = new Kizuna<Config>();
```

### `kizuna generate --check`

```sh title="Terminal"
kizuna generate --check
```

The same work without writing. It names whatever has fallen behind and exits `1`, so a pipeline fails on a generated client nobody regenerated:

```text
  kizuna.types.ts is behind the config
  src/api-client.ts is behind the contract
```

Run it in CI beside your typecheck. See [Breaking changes](/docs/breaking-changes) for the rest of the pipeline, and [Watching](/docs/watching) for regenerating as you edit.

`writeClients` and `checkClients` from `@ts-kizuna/cli` are the same two steps as functions, for a script that does more than the command does.
