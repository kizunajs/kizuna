<AlphaNotice>

Streaming is new. How a route declares a stream, how a handler writes one, and how a client reads one will likely change while v2 is in beta, so pin your version if you depend on it.

</AlphaNotice>

An assistant's reply arrives one token at a time, and a caller who has to wait for the last token before seeing the first stops reading. A long export, a progress report, and a feed of events that has no end share the shape. The route declares what each piece looks like, the handler yields the pieces, and the client reads them as they come.

<Steps>

<Step>

## Declare the stream

A `stream` takes the place of a `body` on the response:

```ts title="src/routes/assistant.ts"
import { z } from 'zod';
import { ProblemDetailsSchema } from 'kizunajs/schemas';
import { k } from '../k';

export const replyRoute = k.route({
    method: 'POST',
    path: '/assistant/reply',
    body: z.object({
        prompt: z.string().min(1),
    }),
    responses: {
        200: {
            stream: {
                delta: z.object({
                    text: z.string(),
                }),
                done: z.object({
                    inputTokens: z.int(),
                    outputTokens: z.int(),
                }),
            },
        },
        400: ProblemDetailsSchema,
    },
});
```

Two `body`s meet on a route like this. The route's own `body` is the request body, the prompt the caller posts, and a streaming route takes one like any other route. The `body` a status would declare under `responses` is the response body, and `stream` takes its place there: a status is sent at once or piece by piece. The `400` is an ordinary Problem Details body, returned or thrown as always. The `200` alone streams.

`stream` is a record of event name to schema, so every message the route sends has a name and a shape. Give it one schema instead when the messages are all alike.

</Step>

<Step>

## Write the handler

The handler returns the status, and for `body` an async generator function. Kizuna sends the status and headers, calls the function, and writes each `yield` the moment it happens:

```ts title="src/routes/assistant.ts"
import Anthropic from '@anthropic-ai/sdk';

const anthropic = new Anthropic();

export const assistant = k.routes.assistant({
    reply: replyRoute.handler(async ({ body }) => ({
        status: 200,
        body: async function* ({ signal }) {
            const stream = anthropic.messages.stream(
                {
                    model: 'claude-opus-5',
                    max_tokens: 64000,
                    messages: [
                        {
                            role: 'user',
                            content: body.prompt,
                        },
                    ],
                },
                {
                    signal,
                }
            );
            for await (const event of stream) {
                if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
                    yield {
                        event: 'delta',
                        data: {
                            text: event.delta.text,
                        },
                    };
                }
            }
            const message = await stream.finalMessage();
            yield {
                event: 'done',
                data: {
                    inputTokens: message.usage.input_tokens,
                    outputTokens: message.usage.output_tokens,
                },
            };
        },
    })),
});
```

Each `yield` names its `event` and carries `data` matching that event's schema, and TypeScript checks the pair, so a `delta` carrying a `done` payload is a compile error. The provider's own events stay inside the handler. What you declared describes your API, and the client on the other side reads `delta` and `done` without knowing which model answered.

The wire is `text/event-stream`, one block per yield, with `data` as JSON:

```
event: delta
data: {"text":"Hel"}

event: delta
data: {"text":"lo"}

event: done
data: {"inputTokens":12,"outputTokens":2}

```

</Step>

<Step>

## Read it

On the streamed status the fetch client hands back `body` as an async iterable. Read it with `for await`, and each message narrows on `event` to its own `data`:

```ts title="chat.ts"
const result = await apiClient.assistant.reply({
    body: {
        prompt: 'Explain server-sent events in one paragraph',
    },
});

if (result.status === 200) {
    let reply = '';
    for await (const message of result.body) {
        if (message.event === 'delta') reply += message.data.text;
        if (message.event === 'done') console.log(`${message.data.outputTokens} tokens`);
    }
}
```

Every other status arrives as it does today, so `result.status === 400` gives a parsed Problem Details body.

In React, append each delta to state and the reply types itself out:

```tsx title="Reply.tsx"
const [reply, setReply] = useState('');

const ask = async (prompt: string) => {
    setReply('');
    const result = await apiClient.assistant.reply({
        body: {
            prompt,
        },
    });
    if (result.status !== 200) return;
    for await (const message of result.body) {
        if (message.event === 'delta') setReply((current) => current + message.data.text);
    }
};
```

### Cancelling

Pass a signal as you would to `fetch`. Aborting it closes the connection:

```ts title="chat.ts"
const controller = new AbortController();

const result = await apiClient.assistant.reply({
    body: {
        prompt,
    },
    fetchOptions: {
        signal: controller.signal,
    },
});

stopButton.onclick = () => controller.abort();
```

On the server the generator's `signal` fires, so an upstream call that took it stops too, and Kizuna returns the generator so a `finally` block runs. The handler above hands `signal` to the Anthropic SDK for this reason.

</Step>

## Messages without names

Give `stream` one schema when every message has the same shape. The handler yields `{ data }`, the wire carries `data:` lines alone, and the client reads `message.data`:

```ts title="src/routes/notifications.ts"
watchEvents: k
    .route({
        method: 'GET',
        path: '/events/watch',
        responses: {
            200: {
                stream: EventRecord,
            },
        },
    })
    .handler(async () => ({
        status: 200,
        body: async function* ({ signal }) {
            for await (const record of db.events.watch(signal)) {
                yield {
                    data: record,
                };
            }
        },
    })),
```

## Ids, retry, and comments

A yield may carry the other two fields a server-sent event has. `id` names the message so a client that reconnects can say where it left off, and `retry` tells it how many milliseconds to wait before it does:

```ts
yield {
    event: 'delta',
    data: {
        text,
    },
    id: `${messageId}:${index}`,
    retry: 5000,
};
```

A `comment` yields a comment line. It carries no data, and it keeps an idle connection open through proxies that close quiet ones:

```ts
yield {
    comment: 'keep-alive',
};
```

The client hands `id` and `retry` back on each message and drops comments.

### Resuming

A client that reconnects sends the last `id` it saw as `Last-Event-ID`. A handler of an event stream receives it as `lastEventId`, and sends what follows:

```ts title="src/routes/notifications.ts"
watchNotifications: k
    .route({
        method: 'GET',
        path: '/notifications/stream',
        responses: {
            200: {
                stream: NotificationSchema,
            },
        },
    })
    .handler(({ lastEventId }) => ({
        status: 200,
        body: async function* () {
            for (const notification of await notificationsAfter(lastEventId)) {
                yield {
                    id: notification.id,
                    data: notification,
                };
            }
        },
    })),
```

The clients reconnect when you turn it on, with `reconnect` in the fetch client and a `ReconnectPolicy` in the Swift and Kotlin clients. As the [event stream specification](https://html.spec.whatwg.org/multipage/server-sent-events.html) has it, they reconnect whenever the connection closes, whether the network dropped it or the server ended the stream, so a proxy closing an idle stream doesn't end it for good. They wait the last `retry` the server sent, longer after reconnections in a row that fail, then send `Last-Event-ID` and carry on yielding to the same loop. `onRequest`, `requestMiddleware` and `requestInterceptor` run again before each reconnection, so a refreshed token goes with it.

To end a stream for good, answer the reconnection with `204 No Content`. Any other status than the stream's own, or a body that isn't `text/event-stream`, fails the stream. Only a `GET`, `HEAD`, `OPTIONS`, `PUT` or `DELETE` stream reconnects, since a `POST` like the assistant route above would run its handler again.

## Answers that outlive the connection

A streamed reply runs inside its request, so it stops when the client goes away, as it does when a phone app goes to the background. To let an answer finish and be read later, start it with one route, write it in a job, and read it with a stream of its own.

Kizuna keeps no stored state, so saving the messages is your app's part. Every other step is Kizuna's:

| Step | Kizuna does | Your app does |
| --- | --- | --- |
| [Start](#start-the-answer) | Queues the job and answers `202` | Saves the prompt |
| [Write](#write-it-in-a-job) | Runs the job, after the request has ended | Calls the model and saves each message |
| [Read](#read-it-back) | Streams, reconnects from the last id, and checks each message with `streamMessageSchema` | Reads the saved messages back |
| [Stop](#stop-it) | | Marks the answer stopped, and aborts the model call |

### Start the answer

The route saves the prompt, queues the work, and answers `202 Accepted` with the answer's id:

```ts title="src/routes/answers.ts"
startAnswer: k
    .route({
        method: 'POST',
        path: '/answers',
        body: z.object({
            prompt: z.string().min(1),
        }),
        responses: {
            202: z.object({
                id: z.string(),
            }),
        },
    })
    .handler(async ({ body, jobs }) => {
        const answer = await db.answers.create({
            prompt: body.prompt,
        });

        await jobs.writeAnswer.queue({
            input: {
                answerId: answer.id,
            },
        });

        return {
            status: 202,
            body: {
                id: answer.id,
            },
        };
    }),
```

On a serverless host, give the jobs a [transport](/docs/jobs#setting-it-up). Without one, `queue` runs the job in the same process, which the host can stop once the response is sent.

### Write it in a job

The job calls the model and saves each message with an id. It runs whether or not anyone is reading:

```ts title="src/jobs.ts"
writeAnswer: k
    .job({
        input: z.object({
            answerId: z.string(),
        }),
    })
    .handler(async ({ input }) => {
        const answer = await db.answers.find(input.answerId);

        for await (const text of replyTo(answer.prompt)) {
            await db.answerMessages.add(input.answerId, {
                event: 'delta',
                data: {
                    text,
                },
            });
        }

        await db.answers.finish(input.answerId);
    }),
```

A model sends many small pieces of text. Join them before saving, so a long answer is a few rows rather than thousands.

### Read it back

The client reads the answer from a `GET` stream. Saved rows come back from the database untyped, so the handler checks each one against `streamMessageSchema`, the schema of one message the route sends:

```ts title="src/routes/answers.ts"
import { streamMessageSchema } from 'kizunajs';

export const answerRoutes = k.routes({
    answerEvents: k
        .route({
            method: 'GET',
            path: '/answers/:id/events',
            responses: {
                200: {
                    stream: {
                        delta: z.object({
                            text: z.string(),
                        }),
                    },
                },
            },
        })
        .handler(({ params, lastEventId }) => ({
            status: 200,
            body: async function* () {
                for await (const saved of db.answerMessages.follow(params.id, lastEventId)) {
                    yield AnswerMessageSchema.parse(saved);
                }
            },
        })),
});

const AnswerMessageSchema = streamMessageSchema(answerRoutes.answerEvents);
```

`follow` is the app's own: it reads what was saved after `lastEventId`, then waits for new rows until the answer is finished. The schema has an arm for every event the route declares, each with its `id` and `retry`, and one for each tool event its `tools` add, so checked messages go straight to [`readToolCalls`](/docs/tools#reading-the-calls).

The clients reconnect a `GET` stream on their own and send the last id they saw, so a dropped connection picks up where it left off. Once the answer is finished and sent, answer the reconnection with `204`, as in [Resuming](#resuming).

### Stop it

A stop route marks the answer stopped, and the job checks the mark and aborts the model call with an `AbortController`. The stream's own `signal` can't stop it, since the work runs in the job, and the signal only reaches the server that holds the connection.

## Raw chunks

A `z.string()` schema with a `text/*` content type, or `BinarySchema` with any other, writes each yield as it is, with no framing around it:

```ts title="src/routes/reports.ts"
exportEvents: k
    .route({
        method: 'GET',
        path: '/events/export.csv',
        responses: {
            200: {
                stream: z.string(),
                contentType: 'text/csv',
            },
        },
    })
    .handler(async () => ({
        status: 200,
        body: async function* () {
            yield 'id,kind,occurredAt\n';
            for await (const record of db.events.all()) {
                yield `${record.id},${record.kind},${record.occurredAt}\n`;
            }
        },
    })),
```

For bytes, hand over a `ReadableStream` in place of the generator. That is how a route passes a file from storage through without holding it in memory:

```ts title="src/routes/reports.ts"
downloadArchive: k
    .route({
        method: 'GET',
        path: '/reports/:id/archive',
        responses: {
            200: {
                stream: BinarySchema,
                contentType: 'application/zip',
            },
        },
    })
    .handler(async ({ params }) => {
        const upstream = await fetch(storage.archiveUrl(params.id));
        return {
            status: 200,
            body: upstream.body,
        };
    }),
```

The client iterates strings for a text stream and `Uint8Array` chunks for a binary one.

## Building the generator elsewhere

An inline generator function sits inside the route's return type, so its event names infer as literals. One declared on its own has nothing to infer from, and TypeScript widens `event` to `string`. Annotate it with `StreamBody`, naming the route and the status:

```ts title="src/routes/canned-reply.ts"
import type { StreamBody } from 'kizunajs';
import { replyRoute } from './assistant';

const cannedReply: StreamBody<typeof replyRoute, 200> = async function* () {
    yield {
        event: 'delta',
        data: {
            text: 'Hello',
        },
    };
    yield {
        event: 'done',
        data: {
            inputTokens: 0,
            outputTokens: 1,
        },
    };
};

export const assistant = k.routes.assistant({
    reply: replyRoute.handler(async () => ({
        status: 200,
        body: cannedReply,
    })),
});
```

## Errors

Before the first message, everything works as on any route: validation answers `400`, a guard `401` or `403`, and `throwError` any status the route declares, all as Problem Details. `throwError` takes no streamed status. A stream is a body to produce, and bailing out is what `throwError` is for.

Once the handler has returned, the status and headers are on the wire. A throw inside the generator after that cannot become a `500`, so Kizuna ends the connection. The client's loop rejects instead of finishing quietly, and the adapter's error callback is told. Declare a terminal event like `done` when the reader must know the reply is whole, and an `error` event of your own when it must know why it stopped short.

With `responseValidation` on, Kizuna validates each message against its schema before writing it, and a message that fails ends the stream the same way.

## Headers

A streamed response goes out with `Content-Type: text/event-stream` and `Cache-Control: no-store`, since a cache stores a complete representation and a stream has none. Return your own `headers` to add to what Kizuna sends, the way you would on any response. `X-Accel-Buffering: no` tells nginx to pass each message through rather than collect them.

Every `GET` route answers `HEAD`, a stream route included: the status and headers, no body, and no `Content-Length`, since the length is unknown. The handler runs, and the generator is never called.

## Tools

A streamed response can name the tools the model may call, adding `tool_call`, `tool_result` and `tool_error` to the events it declares:

```ts
200: {
    stream: {
        delta: z.object({
            text: z.string(),
        }),
    },
    tools,
},
```

Each is discriminated on the tool's dotted key. The handler receives `tools`, whose `run` calls one of those routes as the person streaming and yields its events. See [tools](/docs/tools#running-the-calls).
