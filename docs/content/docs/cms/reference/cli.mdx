---
title: CLI
description: Create the tables, list the pages, and move content between environments through the routes, never a database.
---

Content is not in code, so moving it between a laptop, staging and production is a job for the CLI. `kizuna cms` extends the [kizuna CLI](/docs/cli) and exists wherever `@kizunajs/cms` is installed. It reads `kizuna.cms.config.ts` when the project has one, and `kizuna.config.ts` otherwise. Every command takes `--json` and then prints only machine-readable output, for a coding agent to drive.

## `kizuna cms migrate`

Writes `<timestamp>_kizuna_cms.sql` with the three tables and an index for every collection index into `./drizzle`, or the folder `--out` names. Run it with your other migrations, and again after adding a collection or an index.

```sh
kizuna cms migrate --out drizzle
```

## `kizuna cms check`

Lists published content that fails its schema, what a schema change without a default or a `migrate` step leaves behind, and which earlier version visitors see instead. It exits `1` when there is some. Run it in your deploy against the database the new code will read, so a release stops before visitors see the gap.

```text
Published content that fails its schema:
  page:frontPage, visitors see version 3
    subheading: Invalid input: expected string, received undefined
```

## `kizuna cms migrate-content`

Stores every document at its latest `migrate` step. Reads already run newer steps in memory and the next save stores them, so this is optional: run it after a deploy to stop reads migrating documents nobody edits. It adds no version and publishes nothing.

## `kizuna cms pages`

Lists every page's path and name from the `content.ts` files under `src/app` or `app`, without loading the config.

```text
/                                frontPage
/blog                            blogIndexPage
/blog/[slug]                     articlePage
/contact                         contactPage
```

`--write` also writes the pages module the config imports. `kizuna generate` does that on its own for the module beside the app directory; pass `--app` and `--out` for one kept elsewhere.

## `kizuna cms orphans`

Lists stored content that nothing in the config claims anymore: pages renamed or deleted in code, and the items of a collection that was removed. It exits `1` when there is some, so CI with a database can fail on it.

## `kizuna cms rename-page`

Moves a renamed page's stored content, with its versions and history, to the new name. Rename the page in its `content.ts` first. The command refuses a name that is still a page, and a target that has content of its own.

```sh
kizuna cms rename-page pricingPage plansPage
```

## `kizuna cms rename-site`

Moves a site's stored pages, globals and collections, with their versions, to a new site name. A project that started with `pages` runs it once when it [adds sites](/docs/cms/sites#starting-with-one-site). The command refuses a name that is still declared, and a target that has content of its own.

```sh
kizuna cms rename-site default uk
```

## `kizuna cms import-redirects`

Creates a redirect for each row of a CSV with `from` and `to` columns, like the one HubSpot or a crawl of the old site exports, and skips rows whose `from` already redirects. A `to` that is another row's `from` is collapsed to that row's target, so the import never makes a chain. Use it when [moving from another platform](/docs/cms/seo#moving-from-another-platform).

```sh
kizuna cms import-redirects old-site.csv
```

## `kizuna cms export`

Writes every published item of one collection as JSON, each with its id, to stdout or the file `--out` names. Use it to [move a collection into a table](/docs/cms/content/collections#moving-between-them).

```sh
kizuna cms export employees --out employees.json
```

## `kizuna cms import`

Creates an item of one collection for each record in a JSON file, keeping the record's id, as a draft. Records that fail the collection's schema are listed and skipped, and the command exits `1` when there are any. `--publish` publishes the items that pass.

```sh
kizuna cms import employees employees.json
```

## Environments

`push` and `pull` call each environment's `editing` routes as a signed-in editor, so every copied draft carries a real author. Name them on `cms()`:

```ts title="kizuna.config.ts"
environments: {
    local: {
        url: 'http://localhost:3000/api',
        headers: {
            authorization: `Bearer ${process.env.CMS_LOCAL_TOKEN}`,
        },
    },
    production: {
        url: 'https://example.com/api',
        headers: {
            authorization: `Bearer ${process.env.CMS_PRODUCTION_TOKEN}`,
        },
        production: true,
    },
},
```

## `kizuna cms push`

Copies one page's draft from `local`, or `--from`, into the target as a new draft, with the media it lacks. Published content on the target is never touched.

```sh
kizuna cms push frontPage --to staging
```

Every id a page holds through a [relationship](/docs/cms/connecting#relationships) is checked against the target's own picker list, and missing ids are listed rather than kept silently. The command exits `2` when any are missing.

```json
{
    "page": "frontPage",
    "to": "staging",
    "version": 4,
    "mediaCopied": ["med_3f2a9c1e8b7d4a5f6c0e1d2b"],
    "missingIds": [
        {
            "relationship": "products",
            "id": "prod_tulips",
            "fieldPath": "featured.0"
        }
    ]
}
```

## `kizuna cms pull`

Copies every published page, global and collection item, with its media, from the source into `local`, or `--to`, and publishes it there. Items keep their ids, so references to them still resolve, and content arrives as it is stored, so images keep their crops and focal points. It reads only from the source and refuses a destination marked `production`.

```sh
kizuna cms pull --from production
```
