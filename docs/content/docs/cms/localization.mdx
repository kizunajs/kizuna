---
title: Localization
description: Every page, global and item in every language the site serves, translated field by field or by the model, and published one language at a time.
---

A site in Norway speaks Norwegian and English. Every page, global and collection item has a copy per language, each with its own draft, its own publish state and its own address, so the Norwegian front page can go live on Monday and the English one on Thursday.

## Declaring the locales

Name the languages on `cms()`. The first is the source, the one content is written in before it is translated:

```ts title="kizuna.config.ts"
content: cms({
    db,
    pages,
    locales: ['nb', 'en'],
    auth: {
        identity: 'editor',
    },
}),
```

A locale is a [BCP 47](https://www.rfc-editor.org/rfc/rfc5646) tag, so `de-CH` is as valid as `de`. A site that serves several, like Switzerland, says what to show when a translation does not exist yet:

```ts title="kizuna.config.ts"
locales: ['de', 'fr', 'it'],
fallback: {
    fr: ['de'],
    it: ['de'],
},
```

Without `fallback`, a page that is not translated is not found in that language, which keeps an untranslated page out of search results. A fallback only ever shows a published translation, never the source's draft.

## What is translated

A translator writes the words. A price, a date, an office's coordinates, an `EmployeeId` and an image's crop are the same in every language, and nobody is asked to translate them. Which fields translate follows from the schema:

| Field                     | In a translation                                                          |
| ------------------------- | ------------------------------------------------------------------------- |
| `z.string()`              | Translated                                                                |
| `RichTextSchema`          | Translated                                                                |
| `ImageSchema`             | The file, crop and focal point are shared, and the alt text is translated |
| Numbers, booleans, dates  | Shared                                                                    |
| `z.enum()`                | Shared, and its `options` labels are what the editor shows per language   |
| An id or a relationship   | Shared                                                                    |
| `z.object()`, `z.array()` | Each field inside follows its own schema                                  |

A string that is a code rather than words, like a product number, says so:

```ts
{
    name: 'productCode',
    schema: z.string().max(20),
    localized: false,
},
```

Shared fields live on the source and publish with it. Change the price in the source and publish, and every language shows the new price. A translation holds only the fields that translate, so there is nothing to keep in step. The editor shows a shared field once, in the source, and greyed in a translation with "same in every language", and the model leaves it alone when it translates.

## Reading a language

The page passes the locale it renders. In Next, that is the route's `[locale]` segment:

```tsx title="src/app/[locale]/page.tsx"
export default async function FrontPage({ params }: { params: Promise<{ locale: string }> }) {
    const { locale } = await params;
    const content = await kizuna.content.pages.frontPage.get({
        locale,
    });

    return <h1>{content.heading}</h1>;
}
```

`list`, `getMany` and a global's `get` take `locale` the same way, and a site that serves one language leaves it out. Over HTTP it is `?locale=nb` on every `content` route.

An id is the same in every language. An article holds one `EmployeeId` for its author, and the page reads that employee in the language it renders, so a translation never re-picks what the source chose.

## Addresses

A field that is part of a page's address, like an article's `slug`, is translated like any other, so `/blog/ny-kontor` and `/blog/new-office` are one article. A page that shows a collection reads the item by the slug in that locale:

```tsx title="src/app/[locale]/blog/[slug]/page.tsx"
const { locale, slug } = await params;
const article = await kizuna.content.pages.articlePage.get({
    locale,
    slug,
});
```

Every translation's address is known, so a page can tell search engines about its other languages. [SEO](/docs/cms/seo#languages) covers `hreflang` and the sitemap per language.

## Translating

The editor shows one language at a time, and beside every field, the source's value, so nothing is translated blind. Switch the language in the header, and the form shows that translation's draft with its own publish state and its own reviews.

Ask the model to draft what is missing:

> Translate the front page to Norwegian.

It reads the source and writes the translation as a draft, which a person reads and publishes. A field with a `.max()` holds in every language, so a translation that runs long is caught before anyone sees it.

### Behind the source

Every translation remembers which version of the source it was made from. When a translated field of the English office changes, the Norwegian one shows as **behind** in the editor and in the API, and the page keeps showing it until someone updates it. A change to a shared field, like the office's phone number, reaches every language on its own and flags nothing. The editor lists every translation that is behind, and the model can be asked for the lot:

> Update every Norwegian page that is behind its English.

A translation is never hidden for being behind. An old translation is better than a page that disappears.

## With several sites

With [several sites](/docs/cms/sites), `cms()` declares every locale its sites use, and each site names which it serves. Content every site reads is written once, in the source, and translated into every language a site needs. Country editors draft the translations for their own languages, and an admin publishes them, like any change to that content.

```ts title="packages/content/kizuna.cms.config.ts"
content: cms({
    db,
    locales: ['en', 'nb', 'de', 'fr', 'it'],
    sites: {
        norway: {
            pages: norwayPages,
            app: '../../apps/norway/src/app',
            url: 'https://example.no/api',
            locales: ['nb', 'en'],
        },
        switzerland: {
            pages: switzerlandPages,
            app: '../../apps/switzerland/src/app',
            url: 'https://example.ch/api',
            locales: ['de', 'fr', 'it'],
            fallback: {
                fr: ['de'],
                it: ['de'],
            },
        },
    },
}),
```

Caches are tagged by site and language, so publishing the Italian office refreshes the Italian pages that show it and no other.

## Adding a language later

Add it to `locales`, and every page, global and item gains an empty translation that falls back to nothing until it is written. `kizuna cms check` lists what is untranslated in the new language, and the editor shows the same list, so the work is visible until it is done.
