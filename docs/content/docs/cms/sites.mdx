---
title: Several sites
description: One CMS for a group and its sites. The group's content is written once and every site reads it, and each site keeps content of its own.
---

A group runs several sites: its own, and one for each country it works in. Some content belongs to the group, like the people, the offices and the privacy policy, and every site shows it. Some belongs to one site, like Norway's news. One CMS holds both, and every piece of content has one owner:

- **A page belongs to its site.** It is declared beside its route, in the site's app.
- **A global or a collection belongs to the group or to one site.** Listed on `cms()`, it is the group's. Listed under a site, it is that site's.

## Declaring the sites

Each site is a Next.js app with its own pages. List each under `sites`, with its generated pages module and its `app` directory:

```ts title="packages/content/kizuna.cms.config.ts"
content: cms({
    db,
    sites: {
        group: {
            pages: groupPages,
            app: '../../apps/group/src/app',
        },
        norway: {
            pages: norwayPages,
            app: '../../apps/norway/src/app',
        },
        sweden: {
            pages: swedenPages,
            app: '../../apps/sweden/src/app',
        },
    },
    auth: {
        identity: 'editor',
    },
}),
```

Each site's pages are stored apart, so every app can have a `frontPage`. An app reads its own pages under its site:

```tsx title="apps/norway/src/app/page.tsx"
const content = await kizuna.content.sites.norway.pages.frontPage.get();
```

and `<KizunaPreview content={kizuna.content.sites.norway} />` knows which site it is on.

## The group's content

Globals and collections listed on `cms()` belong to the group. They are stored once, and every site reads them at the same path:

```ts title="packages/content/kizuna.cms.config.ts"
content: cms({
    db,
    sites,
    globals: [PrivacyPolicy],
    collections: [Employees, Offices],
    auth: {
        identity: 'editor',
    },
}),
```

```tsx title="apps/sweden/src/app/contact/page.tsx"
const { items } = await kizuna.content.collections.offices.list();
```

Norway and Sweden list the same offices. An editor who moves an office edits it once, and both sites show the change when it publishes.

## A site's own content

Globals and collections listed under a site belong to that site:

```ts title="packages/content/kizuna.cms.config.ts"
sites: {
    norway: {
        pages: norwayPages,
        app: '../../apps/norway/src/app',
        globals: [Announcement],
        collections: [Articles, Events],
    },
    sweden: {
        pages: swedenPages,
        app: '../../apps/sweden/src/app',
        collections: [Articles],
    },
},
```

They are read under the site, the way its pages are:

```tsx title="apps/norway/src/app/events/page.tsx"
const { items } = await kizuna.content.sites.norway.collections.events.list();
```

Sweden declares no events, so `kizuna.content.sites.sweden.collections.events` fails to compile. Both declare `Articles`, so they share its fields and its `ArticleId`, and each keeps its own items. Norway's blog lists Norway's articles.

## Pointing at the group's content

A site's content holds the group's ids, the way a page holds any collection's. An event names the employee to contact:

```ts title="packages/content/events.ts"
export const Events = defineCollection({
    name: 'events',
    id: EventId,
    fields: [
        {
            name: 'title',
            schema: z.string().min(1).max(80),
        },
        {
            name: 'contactPerson',
            label: 'Contact person',
            schema: Employees.id,
        },
    ],
});
```

The editor's picker lists the group's employees, and the page reads the one the event holds:

```tsx title="apps/norway/src/app/events/[id]/page.tsx"
const { id } = await params;
const event = await kizuna.content.sites.norway.collections.events.get({
    id,
});
const contactPerson = await kizuna.content.collections.employees.get({
    id: event.contactPerson,
});
```

The group's content shows on every site, so it never holds a site's ids. A group collection with an `Events.id` field fails when the config assembles.

## Where the group's data lives

A site holds the group's data by id wherever it lives:

| The data lives in                 | The site holds it through                                                         |
| --------------------------------- | --------------------------------------------------------------------------------- |
| This CMS                          | A group collection, as above                                                      |
| The group's own Kizuna API or CMS | A [relationship](/docs/cms/content#from-another-kizuna-api) fed by its client     |
| A service like Stripe or a CRM    | A [relationship](/docs/cms/content#from-another-service) fed by the service's SDK |

A page is declared beside its route, so a site's pages live in the repository its app does. When the sites share one repository, one CMS holds every site's pages. When a site lives in a repository of its own, it runs a CMS of its own for its pages, and reaches the group's data through a relationship.

## Reading from outside

Every path above is also a route in the `content` group, under the CMS's `apiPath`, so another app or a phone reads the same content over HTTP:

| In process                                              | Over HTTP                                          |
| ------------------------------------------------------- | -------------------------------------------------- |
| `kizuna.content.collections.offices.list()`             | `GET /api/content/collections/offices`             |
| `kizuna.content.sites.norway.collections.events.list()` | `GET /api/content/sites/norway/collections/events` |
| `kizuna.content.sites.norway.pages.frontPage.get()`     | `GET /api/content/sites/norway/pages/frontPage`    |

A [client of the content routes](/docs/cms/api#a-client-for-readers) calls them with the same path, `contentClient.content.sites.norway.collections.events.list()`.

## Editing

Editors work in one editor for the whole group. The switcher lists the group's content first, then each site with its pages, globals and collections. The agent addresses a site's content by its site, so "add an event to the Norwegian site" reaches Norway's `events`, and "update Anna's phone number" reaches the group's `employees`, once for every site.
