Your business runs more than one website. Hagen is a group of plant shops with a group site, a shop in the UK and a shop in Norway. All three show the same people, offices and privacy policy, and each has pages of its own. The UK runs events as well.

That shared library is written once, on `cms()`, and the sites sit beside each other over it:

```text
cms()      employees, offices, privacy policy    every site reads these
group      its pages
uk         its pages, its events
norway     its pages
```

A document is shared or belongs to one site, so an editor always knows where a change lands and which sites it reaches.

## Declaring the sites

A site's shape is `SiteSchema`, with the fields your pages need beside `label`, `url` and `icon`:

```ts title="packages/content/src/sites.ts"
import { z } from 'zod';
import { declareSites } from '@kizunajs/cms';
import { SiteSchema } from '@kizunajs/cms/schemas';
import { pages as groupPages } from './pages/group';
import { pages as countryPages } from './pages/countries';
import { Events } from './events';

export const Site = SiteSchema.extend({
    companyName: z.string(),
});

export const sites = declareSites(Site, {
    group: {
        label: 'Hagen Group',
        url: 'https://hagen.example.com',
        icon: '/icons/group.svg',
        pages: groupPages,
        companyName: 'Hagen Group AS',
    },
    uk: {
        label: 'Hagen UK',
        url: 'https://hagen.example.co.uk',
        icon: '/icons/uk.svg',
        pages: countryPages,
        collections: [Events],
        companyName: 'Hagen UK Ltd',
    },
    norway: {
        label: 'Hagen Norge',
        url: 'https://hagen.example.no',
        icon: '/icons/norway.svg',
        pages: countryPages,
        companyName: 'Hagen Norge AS',
    },
});
```

The shared content goes on `cms()`, beside the sites:

```ts title="packages/content/kizuna.cms.config.ts"
content: cms({
    db,
    collections: [Employees, Offices],
    globals: [PrivacyPolicy],
    sites,
    site: () => process.env.KIZUNA_SITE,
}),
```

`site` says which site a deployment is, and each deployment sets `KIZUNA_SITE`. The pages modules live in the content package too, at `src/pages/group.ts` and `src/pages/countries.ts`, and the apps import the content package, never the other way round. The UK and Norway render the same countries app, deployed twice, so they share one pages module. Each still keeps its own page documents: the UK's `frontPage` and Norway's are edited and published apart. [Deployment](/docs/cms/deployment) shows the repository.

## Reading

A deployment reads its own site's view. On the UK's deployment, offices are the shared offices with the UK's values in place, and events are the UK's own. Every site has offices, so they read straight from `kizuna.content`:

```tsx title="apps/countries/src/app/offices/page.tsx"
const { items: offices } = await kizuna.content.collections.offices.list();
```

`kizuna.content` is typed as any one of the declared sites' views, since the deployment decides which. The countries app serves two sites, and only one of them has events. `of` narrows the content to the sites an app serves, and checking `site` opens what that site has:

```tsx title="apps/countries/src/app/events/page.tsx"
export default async function EventsPage() {
    const content = kizuna.content.of(['uk', 'norway']);

    if (content.site === 'uk') {
        const { items: events } = await content.collections.events.list();
        return <EventList events={events} />;
    }

    notFound();
}
```

The group app narrows the same way, with `kizuna.content.of(['group'])`. The current site itself is typed, custom fields included:

```tsx title="apps/countries/src/app/layout.tsx"
const site = await kizuna.content.site.get();

<footer>{site.companyName}</footer>;
```

`site.get()` returns the site's `key`, like `'uk'`, with its `label`, `url`, `icon`, `locales`, `status` and the fields `Site` adds.

Over HTTP, every content route sits under its site, at `/content/sites/uk/...`, except media at `/content/media`, and a client generated for one site has the same paths as `kizuna.content`. Caches are tagged per site, so a deployment refreshes only what it shows.

## A site's own values on shared content

Every shop shows the shared offices, and the UK answers its phones with its own number. The field says so:

```ts title="packages/content/src/offices.ts"
fields: [
    {
        name: 'address',
        schema: z.string().max(120),
    },
    {
        name: 'phone',
        schema: z.string().max(30),
        perSite: true,
    },
    {
        name: 'openingHours',
        schema: z.string().max(120).optional(),
        sites: ['uk'],
    },
],
```

- **`perSite: true`** lets each site set its own value. A site that leaves it empty shows the shared one, and the editor shows the shared value as the placeholder, with the field marked **Shared** or with the site's label.
- **`sites: ['uk']`** shows and stores the field on those sites alone. A page takes `sites` too, so the countries app's events page exists on the UK alone.

A site's values are that site's draft. Its editors publish them, and only that site refreshes. When a site's editor changes a shared field of the same office too, the editor shows two pending changes: the site's values, which they publish, and the shared change, which goes to review for an admin over every site.

`perSite` cannot go on the id, the slug, or a unique or indexed field, and `defineConfig` throws when it does, since those fields find a document and have to be the same on every site.

## Editors

An editor's sites come from your identity, beside their roles:

```ts title="packages/content/kizuna.cms.config.ts"
auth: {
    identity: 'editor',
    roles: ['editor', 'admin'],
    sites: (editor) => editor.sites,
},
```

`sites` returns a role, or a list of roles, per site, as in `{ uk: 'editor' }`. The role an editor's identity carries itself covers the shared content: `admin` there is an admin over the shared content and every site, and `editor` there drafts shared content and sees no site.

| Editor                  | Shared content              | Their site              | Other sites       |
| ----------------------- | --------------------------- | ----------------------- | ----------------- |
| `admin` over every site | Write and publish           | Write and publish       | Write and publish |
| `admin` on a site       | Draft, and ask for a review | As `admin` on one site  | Not shown         |
| `editor` on a site      | Draft, and ask for a review | As `editor` on one site | Not shown         |
| `editor` with no site   | Draft, and ask for a review | None                    | Not shown         |

Inside a site, the [one-site rules](/docs/cms/editing/permissions#on-one-site) apply as they are. Shared content reaches every site, so an admin over every site publishes it. A site's editor never sees another site, in the admin, the API or MCP. [Who can do what](/docs/cms/editing/permissions#with-several-sites) shows each editor's screen.

## Images

Each site has images of its own beside a shared library. Shared content holds shared images, and a site's content holds its own and the shared ones. Every editor may upload to the shared library, and changing or deleting a shared image takes an admin over every site, since every site shows it.

## Publishing

Before a shared document publishes, the editor shows where it appears on each site: the pages whose content holds it, and the pages that listed it when they last rendered.

The list names partners under their label too. Publishing then refreshes every site and partner that shows the document, and unpublishing and deleting do the same. Each one gets a job of its own, which calls its `invalidate` with what changed:

| Body            | Refreshes                                |
| --------------- | ---------------------------------------- |
| `{ brand, id }` | The item, and the pages that hold its id |
| `{ global }`    | A global, like `{ global: 'settings' }`  |
| `{ page }`      | A page, like `{ page: 'frontPage' }`     |

A declared site's `invalidate` is at its `url`, `apiPath` and `path`, as in `https://hagen.example.co.uk/api/invalidate`. The call carries a `kizuna-cms-signature` header, an HMAC of the body made with `KIZUNA_CMS_PREVIEW_SECRET`, which every app already shares, and valid for five minutes. Anything else calling `invalidate` uses the credential `auth.invalidate` names.

Each publish records one row per site and partner, with its status and attempts: `queued` waits for its turn, `answered` refreshed, `retrying` did not answer and is tried again, and `failed` will not be. The editor reads them from `GET /editing/refreshes?ref=`, which lists the latest publish's refreshes, and shows how it went:

### Running the refreshes

A config with sites gets the CMS's own job, `content.refreshSite`, beside your [jobs](/docs/jobs), so it names a `jobRunner`. With `mode: 'in-process'`, the job runs on its own. With `mode: 'http'`, the job endpoints need an identity, and the CMS's job declares none, so your own jobs name it. A [transport](/docs/jobs#transports) retries a site or partner that does not answer, up to five attempts. Without one, a refresh that fails is not tried again.

## Partners

A partner is a business outside Hagen that shows Hagen's content on its own website. A travel agency sells Hagen UK's garden workshops as day trips, so it reads the UK's events and offices. A partner only reads, so it has no pages or editors here, and the site switcher leaves it out.

```ts title="packages/content/kizuna.cms.config.ts"
content: cms({
    sites,
    partners: {
        travelAgency: {
            label: 'Travel agency',
            reads: ['uk'],
            invalidate: {
                url: 'https://travel.example.com/api/invalidate',
                headers: () => ({
                    authorization: `Bearer ${process.env.TRAVEL_AGENCY_TOKEN}`,
                }),
            },
        },
    },
}),
```

### What it reads

`reads: ['uk']` is the UK's view and the shared content: the offices with the UK's phone numbers, and the UK's events.

Content routes are public until `auth.read` names an identity. Then every content route, media included, requires that identity, and each partner's `reads` limits what its token may read. A read of Norway answers `403`, naming the permission it lacks, `content.sites.norway:read`. A token whose guard returns no `partner` reads every site, which suits your own apps.

### How it signs in

The travel agency signs in with OAuth client credentials. Your authorization server issues it a client, and an `openIdConnect` identity verifies its tokens as on [OAuth](/docs/oauth). `auth.read` names that identity:

```ts title="packages/content/kizuna.cms.config.ts"
auth: {
    identity: 'editor',
    roles: ['editor', 'admin'],
    sites: (editor) => editor.sites,
    read: 'partner',
},
```

The guard maps the token's client to the partner's name and returns it as `partner`, as in `{ partner: 'travelAgency' }`, and the CMS takes the sites that partner may read from its `reads`. The CMS verifies tokens and never issues them. A read with a token answers with `Cache-Control: private`, so no shared cache keeps it.

### What it installs

The partner installs the [client you publish](/docs/cms/api#publishing-a-client) for the UK, a package with the client and the id brands, and calls it with its token:

```ts title="src/lib/hagen.ts"
import { createClient } from '@hagen/uk-content';
import { partnerToken } from './partner-token';

export const hagen = createClient({
    baseUrl: 'https://hagen.example.co.uk/api',
    onRequest: async ({ headers }) => {
        headers.set('authorization', `Bearer ${await partnerToken()}`);
    },
});
```

A partner that runs Kizuna CMS itself holds your ids through a [relationship](/docs/cms/relationships#from-another-kizuna-api).

### How it hears a publish

When a document it reads publishes, the CMS calls the partner's `invalidate` with the same bodies a site gets, `{ brand, id }`, `{ global }` or `{ page }`, and the bearer token the partner gave you. The body carries no content, so the partner reads the document again through its client, and a document that was unpublished or deleted answers `404`. A partner hears only what it reads, so a change to Norway never reaches the travel agency. The editor counts partners beside sites, so publishing a shared office reads "Refreshed 2 of 3 sites and 1 partner. Hagen Norge did not answer, retrying." while Norway is down.

## Sites created by admins

Forty dealers, each with a site and its domains, on one app and one deployment. A developer never hears about a new site, since an admin creates it in the editor:

```ts title="src/cms/site.ts"
export const Site = defineSite({
    fields: [
        {
            name: 'theme',
            schema: z.enum(['classic', 'bold']),
            options: {
                classic: 'Classic',
                bold: 'Bold',
            },
        },
        {
            name: 'phone',
            schema: z.string().max(30),
        },
    ],
});
```

```ts title="kizuna.config.ts"
content: cms({
    db,
    pages,
    collections: [Services],
    sites: Site,
}),
```

The admin who creates a dealer's site picks its key, and gives it its label, its `domains` and the fields above. The deployment picks the site from the domain a request arrives at. A dealer's editors come from your identity's `sites`, under the dealer's key, and see their site alone. All forty sites share one deployment, so a publish refreshes that deployment once. The rules below hold for these sites as for declared ones.

## Starting with one site

A project with one site stores its pages under the site `default`. Content on `cms()` is shared from the start, so adding `sites` moves none of it, and one command gives the pages to their site:

```sh
kizuna cms rename-site default group
```

## The rules between sites

1. A document is shared or belongs to one site.
2. A site reads the shared content and its own, never another site's.
3. Names are unique within a site and the shared content.
4. A site's value for a field shows in place of the shared one, and an empty value shows the shared one.
5. Inside a site, the one-site roles apply, and an admin over every site publishes shared content.
6. Publishing refreshes every site and partner that shows the document, and one that is down never holds up the others.
7. Sites are addressed by their key, like `uk`.
8. Each language is its own copy of a document.
