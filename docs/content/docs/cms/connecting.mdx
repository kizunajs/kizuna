## Relationships

A field holds the id of a record, and the page fetches the record.

### Within this CMS

An article's author is an employee. The field is the collection's id type, and the picker lists the employees:

```ts
{
    name: 'author',
    schema: Employees.id,
},
```

```tsx
const author = await kizuna.content.collections.employees.get({
    id: article.author,
});
```

Every article by one author is a `where` on the field. Deleting an employee that articles hold is refused, and the editor lists the articles.

### From your own API

A record in your own tables. `defineRelationship` gives the editor the list to pick from, through a route that returns id, label and image:

```ts title="src/cms/relationships.ts"
export const Products = defineRelationship({
    name: 'products',
    id: ProductId,
    options: async ({ query, ids, headers }) => {
        const result = await apiClient.products.listProductOptions({
            query: {
                q: query,
                ids,
            },
            headers,
        });
        return result.status === 200 ? result.body.options : [];
    },
});
```

It runs as the editor, so your route decides what they see. The page holds `z.array(Products.id)` and fetches the products itself:

```tsx
const featured = inStoredOrder(content.featured, result.body.products, (product) => product.id);
```

### From another Kizuna API

Every collection serves its options, so another Kizuna CMS's content client is the picker:

```ts
options: async ({ query, ids }) => {
    const result = await headOffice.content.collections.employees.options({
        query: {
            q: query,
            ids,
        },
    });
    return result.status === 200 ? result.body.options : [];
},
```

### From another service

A Stripe id gets a brand of its own, `StripeProductId`, and `options` calls Stripe with your key. When a product changes there, a webhook route calls `invalidate` with the relationship's name, and every page that holds it refreshes.

## Events

A collection names what happens after it publishes, with `plugins` and `jobs` like a route handler:

```ts
on: {
    published: async (product, { plugins, jobs }) => {
        await plugins.medusa.upsertProduct(product);
        await jobs.indexProduct.queue({
            input: {
                id: product.id,
            },
        });
    },
    deleted: async (product, { plugins }) => {
        await plugins.medusa.removeProduct(product.id);
    },
},
```

`published`, `unpublished` and `deleted`. They run after the write and cannot change it. An error is logged and the publish stands. Drafts have no event. `on` on `cms()` runs for every document.

Validation is the field's schema, access is `auth`, and derived values belong to the page. None of them are events.

## The content API

The CMS routes come in three groups:

| Group        | Called by                | What it holds                                 |
| ------------ | ------------------------ | --------------------------------------------- |
| `content`    | Anyone                   | Published pages, globals, items and images    |
| `editing`    | Editors and their agents | Drafts, publishing, versions, reviews, search |
| `invalidate` | Your app                 | Refreshing pages that hold an id that changed |

`GET /api/content/collections/employees` is the REST API. Every collection also serves `.../options`, and a site's content is under `/content/sites/<site>/...`.

### A client for readers

```ts title="kizuna.config.ts"
clients: [
    fetchClient({
        output: './src/lib/content-client.generated.ts',
        groups: ['content'],
    }),
],
```

`contentClient.content.pages.frontPage()` over HTTP reads what `kizuna.content.pages.frontPage.get()` reads in process. Swift, Kotlin and OpenAPI take `groups` the same way.

### Publishing a client

Another repository installs the client as a package. Generate it for the site it serves, put it in a package of its own, and publish it where your packages go. `kizuna diff` fails a release that would break it.

```ts
fetchClient({
    output: './packages/uk-content/src/index.ts',
    groups: ['content.sites.uk', 'content.globals', 'content.collections', 'content.media'],
}),
```

### Content in the app API

A mobile app reads content through a route on your API, which reads the CMS in process:

```ts
.handler(async () => {
    const { items } = await content.collections.articles.list({
        select: ['title', 'image'],
        limit: 20,
    });
    return {
        status: 200,
        body: {
            articles: items,
        },
    };
}),
```

Set `media.publicPath` to a full URL so image URLs are absolute.

### Talking to the app

When your app changes a product, it calls `invalidate` with the relationship's name and the id, through the CMS client, as the identity `auth.invalidate` names. Every page that shows the product refreshes.

### A config of its own

When the site has an app API too, give the CMS its own `kizuna.cms.config.ts`, mounted at its own `apiPath`, so editors, content tools and content clients never mix with the app's.
