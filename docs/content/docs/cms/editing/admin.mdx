Some work needs room. Tagging forty articles, finding last week's orders, or reading a page beside the site it changes is easier on a full screen than in a chat. The admin is that screen. It saves to the same drafts as the chat and the page, under the same rules, so an editor moves between them freely.

## Signing in

The admin is at `/admin` under the CMS's routes, so `/api/admin` with the default `apiPath`. Editors sign in as the editor identity under `auth` on `cms()`, through your app's own auth. Kizuna keeps no accounts and stores no passwords, so you hand it the call that signs an editor in, and the admin draws its own sign-in screen at `/admin/login`. Here `auth` is a [Better Auth](https://better-auth.com) instance:

```ts title="kizuna.config.ts"
content: cms({
    auth: {
        identity: 'editor',
        signIn: ({ email, password, headers }) =>
            auth.api.signInEmail({
                body: {
                    email,
                    password,
                },
                headers,
                asResponse: true,
            }),
    },
}),
```

`signIn` returns the response your auth answers with. Its cookies reach the browser, and any status outside 2xx tells the editor their email or password is wrong, in the same words whichever one it was. A signed-out editor who opens the admin or draft mode lands on the screen, and comes back to where they were going once they are in. The CMS checks that the form was sent from a page of your site, so a form on another site cannot sign an editor in to an account of its choosing.

Give the site its `name`, and the sign-in screen asks the editor to sign in to it, as in **Sign in to Hagen**. Each tab of the admin carries it too, after the screen's title, like Front page · Hagen:

```ts title="kizuna.config.ts"
content: cms({
    name: 'Hagen',
    auth: {
        identity: 'editor',
    },
}),
```

The foot of the sidebar shows who is signed in, with their role. Their name opens a menu with their email when [`people.list`](/docs/cms/editing/reviews#people) gives one, the theme and, when the API serves MCP, **Edit in your chat**, which shows how to connect Claude as them, as in [Agents and tools](/docs/cms/editing/agents#connecting-a-chat). Give `signOut` the call that ends a session, and the menu adds **Sign out**, which ends the session, closes draft mode, and returns to the sign-in screen:

```ts title="kizuna.config.ts"
content: cms({
    auth: {
        identity: 'editor',
        signOut: ({ headers }) =>
            auth.api.signOut({
                headers,
                asResponse: true,
            }),
    },
}),
```

### Signing in elsewhere

When editors sign in somewhere else, like your company's single sign-on, name that page as `signInPath`. A signed-out editor goes there with `next` naming where they were going. Name the route that ends a session as `signOutPath`, and **Sign out** links to it, so it answers `GET`:

```ts title="kizuna.config.ts"
content: cms({
    auth: {
        identity: 'editor',
    },
    signInPath: '/sso',
    signOutPath: '/logout',
}),
```

Each pair takes one or the other. `cms()` throws when given both `signIn` and `signInPath`, or both `signOut` and `signOutPath`.

## Its address

Editors bookmark the admin, so give it an address they remember. `adminPath` is the path from your site's root, and the sign-in screen sits under it, at `/admin/login`:

```ts title="kizuna.config.ts"
content: cms({
    auth: {
        identity: 'editor',
    },
    adminPath: '/admin',
}),
```

A path under `apiPath` is served by the mount you already have. Anywhere else, like `/admin` above, mount the config a second time at the site's root, from an optional catch-all route at the admin's path:

```ts title="src/app/admin/[[...admin]]/route.ts"
import kizuna from '@kizuna-config';

export const { GET, HEAD } = kizuna.api.mount();
```

With no `basePath`, the route matches the path as the browser sent it, so this file serves `/admin` and `/admin/login`. The admin calls the CMS's routes at `apiPath` wherever it is served, signing in and out among them, and an editor who signs in comes back to `adminPath`.

## The sidebar

The sidebar opens on the [dashboard](/docs/cms/dashboard), and lists everything the editor may open under headings. A heading comes from `group` on a global, collection or view:

```ts title="src/cms/orders.ts"
export const Orders = defineView({
    name: 'orders',
    group: 'Shop',
    fields: orderFields,
    list: searchOrders,
    get: getOrder,
});
```

Pages sit under Content, and so does anything without a `group`. A view the editor may not see is left out, along with whatever else their [access](/docs/cms/editing/access) keeps from them.

⌘K, or Ctrl+K off a Mac, searches everything in the sidebar and every page and item by its title, with pages and each collection's items under a heading of their own. The arrow keys move through what it finds, Enter opens it, ⌘Enter opens it in a new tab, and Escape closes the search.

Under **Actions** it offers what the open document's buttons do: **Publish**, **Save draft**, **Ask for review**, **Open on the site** and the collection's own actions, each where its button would be offered, and asking first where the button asks. On any other screen, Actions creates a new item of each collection, as in **Create new article**.

On a phone, the sidebar opens as a sheet from the menu button at the top left, with the search beside it on the right.

Every screen opens with the same header: the trail back to the dashboard, the screen's title, a line of facts like a count or when it last changed, and its actions on the right.

## Lists

Pages, each collection and each view open as a list: a table with the title of every row, its path under it, where it stands, and when it last changed. The header counts the rows and offers **Create new**. The search box finds rows by title or path, and a click on a column's heading sorts by it, as **Sort** does.

A collection's list asks the server for each page it shows, with the search, filters and sort, through the same [list route](/docs/cms/editing/agents#listing-items) a model calls. It sorts by title, status, when an item last changed, and the fields of the collection's `indexes`, which the store keeps an index for.

**Filters** builds conditions from the item's status and from the fields of a collection's `indexes` that hold a choice or an id:

```ts title="src/cms/content.ts"
export const Articles = defineCollection({
    name: 'articles',
    id: ArticleId,
    fields: articleFields,
    indexes: ['topic', 'author'],
});
```

Rows joined by **And** must all hold, and **Or** starts another set that may hold instead. A field holding ids of a collection with a `tree` adds **is within** and **is outside**, which take in everything under the item picked as well.

**Columns** shows and hides columns, like who saved each row last, and the admin remembers the choice in that browser. A collection offers every field of its `indexes`, and shows the fields its `columns` names until you hide them:

```ts title="src/cms/content.ts"
export const Articles = defineCollection({
    name: 'articles',
    id: ArticleId,
    fields: articleFields,
    indexes: ['topic', 'publishedOn'],
    columns: ['topic', 'author'],
});
```

A choice shows the label of its option, like Plant care, and an id shows the title of the item it names. Only the fields of `indexes` sort, so here Author shows in the list and its heading sorts nothing.

A long list comes in pages, 25 rows to a page until you pick another number.

Tick rows and their actions take the header's place: **Publish**, **Unpublish** and, for items, **Delete**, each asking first, as a single publish does. **Select all** ticks every row the search and filters keep, across pages. An item that refuses stays ticked, with the reason under the header.

A collection with a `tree` lists its items nested under their parents, until you search, filter or sort. Drag a row onto another to move it under that one.

A view's list shows its `title` and `columns`, a choice by the label of its option, and the search box asks its `list` function, which looks in the fields `search` names. A view that names [`filters` or `sorts`](/docs/cms/views#filtering-sorting-and-paging) gets **Filters**, **Sort** and the pager a collection has, and its `list` filters, sorts and pages on the server. Without them, `list` takes the search alone, and the admin sorts and pages the records it returns. The app keeps the records, so a view's list has no **Create new** and no tick boxes.

## Media

**Media**, under Content, shows every uploaded image with its file name, size and how many pages use it. The header counts the images, the ones nothing uses, and the space they take. **All images** and **Unused** pick which show, and **Grid** and **List** pick how. The search box finds an image by its file name or alt text, **Type** keeps one format, and **Sort** orders them by when they arrived, by name or by size.

**Upload**, or files dropped on the screen, adds JPEG, PNG, WebP, GIF and AVIF images. Each is checked by its bytes and loses its location metadata, and the same file uploaded twice is one image.

A click on an image opens it beside the grid: the image large, its alt text, its type, size and who uploaded it, and every page that uses it, each a link to that page with the field that holds the image. Click the image to set its focal point, the spot a crop keeps in frame, and **Save** keeps both.

The library's alt text and focal point are the image's own, and each use can set its own instead. A field that picks the image starts with its alt text, and a page shows it wherever the field's is empty. The focal point holds wherever a field sets none. A crop, focal point or alt text set in a field belongs to that use alone, so a change on one page never moves the image on another. Saving in the library refreshes every page that shows the image.

**Delete**, in the `…` menu, asks first and says how many pages use the image. Those pages lose it, so give each of them another image before deleting one that is in use.

## Editing

A document opens with its title large and its actions on the right: **Save draft**, **Publish**, and a `…` menu. Someone asked to review it also gets **Review**, which puts what is live beside the draft, field by field, with the request's note and each reviewer's answer, as in [Reviews](/docs/cms/editing/reviews). Under the title a line says where it stands, when it last changed and who saved it, and who owns it, where you can pick another owner. The menu holds **Ask for review**, which sends it to someone to look at first as in [Reviews](/docs/cms/editing/reviews), **Unpublish** once it is live, whose message offers **Undo** to publish it again when the draft held no changes, and for an item **Duplicate**, the collection's own [actions](/docs/cms/collections#actions) and **Delete**.

The draft saves a moment after you stop typing, and the header says when it last did. **Save draft** saves at once, and **Publish** lists every change and asks you to confirm. While a required field is empty, Publish waits and says which field it waits for, like "Fill in Department before publishing". A click on that line takes you to the field, which says it is needed.

When a save does not reach the CMS, **Save draft** reads **Not saved**, with why beside it, and **Offline** shows while the browser has no connection. Your changes stay on the screen. **Retry now** sends them again, and the draft saves on its own once you are back online. Publish waits until it has.

A document your role may not change says so, with the way back to its list, and an address that names no document, like a deleted article, offers its list and the search.

Under the title, **Edit** shows the fields and **Versions** counts the saved versions. At the other end of that row, **Live preview** puts the site beside the fields and **Info** lists the document's status, owner, page, and when it was created, last updated and last published.

- **Edit** lays the fields out with their [layout](/docs/cms/fields#layout): tabs over the fields, rows side by side, collapsible sections, and the fields marked `position: 'sidebar'` in a column on the right. A document with no sidebar fields gives the main column the full width.
- **Versions** lists every saved version, newest first and ten to a page, with where it stood and who saved it. **Compare** opens a version beside the current draft, side by side or inline, and **Only changed fields** hides the fields they share. The other versions are listed beside it to compare with instead. **Restore this version** asks first, then makes that version the draft, which you [publish](/docs/cms/editing/drafts) as usual. The draft you had stays under Versions, and **Undo** on the message that follows brings it back until you change the draft again.

**Live preview** puts your site in [draft mode](/docs/cms/next#draft-mode) beside the fields, with the sidebar's fields moved under the main ones, at the Desktop, Tablet or Mobile width the select above it picks. What you type shows on the page as you type it, through [live updates](/docs/cms/next#live-updates). A page opens at its own path, and an item at the page its collection's [`preview`](/docs/cms/collections#live-preview) names, its own page, or the first page that holds it. An item no page shows has no Live preview.

Each field has its label above it, with an asterisk when the document needs it before it can publish, and its help text under it. A field the server refuses shows why at its top right.

A field made of other fields, like a page's hero block, shows them under its name as a heading, or under its tab when a tab holds it alone. A list shows each item as a row: drag it by the handle or move it with the arrow keys, open it with the chevron to edit its fields, and remove it with the ×, which **Undo** on the message that follows puts back. A row shows the item's first text as its title, and a block's name before it. **Collapse all** and **Expand all** sit beside the list's label, and the add button under the rows names the item, like **Add link** for a list labelled Links.

An image shows its file name and size, and in the sidebar the image itself, large. An empty one takes an image from the library, or a file dropped on it. Edit opens the image at size: click it to set the focus a crop keeps in view, write its alt text, and trim pixels from its edges under **Crop**. **Apply** keeps the changes.

A field that holds one id of a collection or a [relationship](/docs/cms/relationships) picks it from a search. A list of ids shows a row for each, with its image and detail, in the order you drag them into. **Choose products**, named after the field, opens a sheet that searches as you type, ticks what the list holds, and counts it against the list's maximum. **Use 3 products** puts your choice in the field.

A choice shows the label of the option picked. A field named `slug` shows its value locked, since changing a slug moves the page it names. **Unlock** makes it editable. A text field counts its characters once it nears its limit.

## Styling

The admin can wear your brand. Its styles sit in a cascade layer named `kizuna`, so a rule of yours outside that layer wins over them whatever its specificity. Name your stylesheet as `adminCss`, a path on your site or a full URL, and the admin loads it after its own:

```ts title="kizuna.config.ts"
content: cms({
    auth: {
        identity: 'editor',
    },
    adminCss: '/cms-admin.css',
}),
```

In Next.js, `public/cms-admin.css` is served at that path. The sign-in screen loads it too, and so does the editor in the chat, which reads a path from the site at `preview.url`.

Every class follows one pattern: a block per component, like `k-card`, its parts after two underscores, `k-card__link`, and a variant after two hyphens, `k-button--primary`. State that changes as the editor works, like the open item of a list or the current page in the sidebar, is an attribute rather than a class, such as `[data-panel-open]` or `[aria-current='page']`. To set a document's title larger:

```css title="public/cms-admin.css"
.k-page-header__title {
    font-size: 32px;
}
```

The blocks you are most likely to restyle:

| Block             | What it is                                                                          |
| ----------------- | ----------------------------------------------------------------------------------- |
| `k-sidebar`       | The sidebar, with `__item`, `__heading`, `__count` and `__account`                  |
| `k-page-header`   | Every screen's header, with `__trail`, `__title`, `__meta`, `__actions` and `__bar` |
| `k-dashboard`     | The dashboard, with `__tiles`, `__panels` and `__range`                             |
| `k-stat`          | A stat tile, with `__label`, `__value` and `__detail`, and its `k-change` badge     |
| `k-chart`         | A chart panel, with `__line`, `__line--previous`, `__bar`, `__legend`, `__tooltip`  |
| `k-card`          | A collection on the dashboard, with `__link`, `__count` and `__add`                 |
| `k-list`          | A collection's list, with `__search`, `__row` and `__title`                         |
| `k-media-tile`    | An image in the media library, with `__thumb`, `__name` and `__detail`              |
| `k-media-details` | The open image beside the library, with `__frame`, `__uses` and `__facts`           |
| `k-field`         | One field of a form, with `__label` and `__control`                                 |
| `k-array`         | A list field, with `__row`, `__index`, `__tag`, `__title` and `__panel`             |
| `k-button`        | A button, with `--primary`, `--secondary` and `--small`                             |
| `k-input`         | A text input, and the trigger of a select                                           |

Colours and sizes are custom properties on `:root`, like `--k-ink`, `--k-muted`, `--k-surface` and `--k-radius-card`, which the admin sets again under `[data-theme='light']` when the system is light. A stat's change badge is the one place the admin uses colour, through `--k-change-up`, `--k-change-down` and `--k-change-none`, each with a `-surface` for its background.

## The admin, the page and the chat

All three write the same drafts through the same `editing` routes, so a rule the admin keeps holds for a model too. What differs is how much room each has:

|                     | The admin                  | MCP tools               | A view in the chat           |
| ------------------- | -------------------------- | ----------------------- | ---------------------------- |
| Signing in          | Your editor identity       | OAuth, through the host | The host signs in            |
| Dashboard           | Widgets and charts         | The numbers, as data    | No                           |
| Lists, bulk actions | Search, filters and paging | Change many at once     | No, long lists need room     |
| Editing fields      | Tabs, rows and sidebar     | Saves drafts by field   | A quick change of a field    |
| Live preview        | Beside the fields          | No                      | Depends on the host's frames |
| Versions            | Compare and restore        | List and restore        | No                           |
| Publishing          | Publish, after a confirm   | Always asks first       | The approval, as a card      |
| Actions, like Send  | Buttons                    | One tool per action     | The confirm, as a card       |

A model reads a collection the way the admin lists it, and a nested collection like [tags](/docs/cms/collections#trees) arrives as its tree. [Agents and tools](/docs/cms/editing/agents) lists the tools.
