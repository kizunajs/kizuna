---
title: Media
description: Upload images once to any S3-compatible store, keep the original, and crop per use.
---

An image is uploaded once. Every use of it on a page stores its own crop, focal point and alt text, so cropping a photo for the spring hero changes nothing on the about page.

## Storage

Files live in an S3 bucket, through the AWS SDK, so any S3-compatible store works. Point it at yours with environment variables, or the same names under `media` on the plugin:

| Variable                   | What it is                                                                          |
| -------------------------- | ----------------------------------------------------------------------------------- |
| `CMS_S3_BUCKET`            | The bucket                                                                          |
| `CMS_S3_ENDPOINT`          | The store's S3 endpoint for Supabase Storage, Cloudflare R2 or MinIO. Unset for AWS |
| `CMS_S3_REGION`            | `auto` for R2, your project's region for Supabase, the bucket's for AWS             |
| `CMS_S3_ACCESS_KEY_ID`     | Falls back to the SDK's own lookup                                                  |
| `CMS_S3_SECRET_ACCESS_KEY` | Falls back to the SDK's own lookup                                                  |

Supabase, for one:

```ts
media: {
    endpoint: 'https://abcdefgh.storage.supabase.co/storage/v1/s3',
    region: 'eu-north-1',
    bucket: 'cms',
},
```

The bucket can stay private: images reach the browser through the image route, never from the bucket. Without a bucket, development keeps files in memory and production refuses to start.

## Uploads

The preview handles uploading. Underneath it is three calls: `POST /media/uploads` with the name, type and size answers a presigned URL, the browser `PUT`s the file there, and `POST /media/uploads/:uploadId` checks the file and creates the media item. Paths here are relative to where the CMS routes are served.

The check reads the bytes with sharp, never the name or the declared type. SVG is refused, since it is a document that can carry script. A file with EXIF, where a camera writes the location, is re-encoded without it; a file without metadata is stored as uploaded. Files over the limit, ten megabytes unless `media.maxBytes` says otherwise, are refused before the upload starts.

The media id is a hash of the stored bytes, so the same file uploaded twice is one item, and `kizuna cms push` can tell what another environment already has.

## The stored value

`ImageSchema` stores the media id and the overrides for that use, as fractions of the original so they survive any resize:

```json
{
    "id": "med_3f2a9c1e8b7d4a5f6c0e1d2b",
    "alt": "Tulips in the morning",
    "crop": { "x": 0.1, "y": 0, "width": 0.8, "height": 1 },
    "focalPoint": { "x": 0.5, "y": 0.3 }
}
```

## What the page receives

`Output` turns the reference into `{ id, url, alt, width, height }`. `width` and `height` are the size the crop leaves, and `url` is the image route with the crop and focal point as its query:

```text
/cms-api/media/med_3f2a9c1e8b7d4a5f6c0e1d2b/image?crop=0.1,0,0.8,1&focal=0.5,0.3
```

The image route, `GET /media/:id/image`, is public, renders the stored file with sharp, and answers WebP with a year of `immutable` caching, since the id names the bytes and the query names the crop. It also takes `w` and `h`; with both, the image is cut to that shape around the focal point. `next/image` takes the URL as it is.

Set `media.publicPath` when the api is mounted somewhere other than `/api`.

## Alt text and focal points

Each media item carries a default alt text and focal point, which the preview and the agent set with `PATCH /cms/media/:id`. A field's own values win where set.
