Every page gets a search result. Three steps set it up, and editors take it from there.

<Steps>

<Step>

## Name the site

Every search title ends in the site's name, written once:

```ts title="kizuna.config.ts"
content: cms({
    db,
    pages,
    metadata: {
        title: ({ title, site }) => `${title} | ${site.label}`,
    },
}),
```

`site` is the current site, so with [several sites](/docs/cms/sites) each one's titles end in its own label. A project with one site takes its label from `name` on `cms()`. A title that already ends in the site's name, like the front page's "Acme Blog", gets nothing added.

</Step>

<Step>

## Render it

Each page exports its metadata:

```tsx title="src/app/blog/[slug]/page.tsx"
export const generateMetadata = kizuna.content.pages.articlePage.metadata;
```

That renders the title, description, canonical address, robots tag, Open Graph and Twitter tags, and the page's other languages. Spread it to add your own.

</Step>

<Step>

## Mark the fields it starts from

An article has a title, a teaser and a cover. Mark which field each part of the search result starts from:

```ts title="src/cms/articles.ts"
export const Articles = defineCollection({
    name: 'articles',
    fields: [
        {
            name: 'title',
            schema: z.string().max(80),
            metadata: 'title',
        },
        {
            name: 'teaser',
            schema: z.string().max(200),
            metadata: 'description',
        },
        {
            name: 'cover',
            schema: ImageSchema,
            metadata: 'image',
        },
    ],
});
```

Every article now has a search result: its title, its teaser and its cover. An editor who wants something else for search writes it in the editor, below.

</Step>

</Steps>

## What editors change

Each article starts with what the code gave it. An editor changes it for one article:

|              | Starts as                                           | The editor can      |
| ------------ | --------------------------------------------------- | ------------------- |
| Title        | The article's title, then "\| Acme Blog"            | Write another       |
| Description  | The article's teaser                                | Write another       |
| Image        | The article's cover                                 | Pick another        |
| Title suffix | "\| Acme Blog", unless the title ends in it already | Pick No suffix      |
| Index        | Yes                                                 | Switch it off       |
| Follow       | Yes                                                 | Switch it off       |
| Canonical    | The page's own address                              | Point it at another |

What it starts as shows as the placeholder, and clearing a field goes back to it. A page with Index off is left out of the sitemap too. Try it, open Tags to see what the page renders, then open Front Page, whose title is the site's name:

## Structured data

Search engines and AI answers read a page's facts from JSON-LD, a script tag that says in a fixed vocabulary what the page is about: an office's address and opening hours, an article's author and date. Google uses it for the details it shows beside a result.

Render it with the item the page shows:

```tsx title="src/app/offices/[id]/page.tsx"
export default async function OfficePage({ params }: PageProps<'/offices/[id]'>) {
    const office = await kizuna.content.pages.officePage.get(await params);

    return (
        <main>
            <JsonLd type="LocalBusiness" of={office} />
            <h1>{office.name}</h1>
        </main>
    );
}
```

The page gets:

```html
<script type="application/ld+json">
    {
        "@context": "https://schema.org",
        "@type": "LocalBusiness",
        "name": "Harbour Office",
        "address": "12 Harbour Street",
        "telephone": "+44 20 0000 0100",
        "openingHours": "Mo-Fr 08:00-16:00"
    }
</script>
```

Each type reads the item's fields by name:

| Type             | Reads                                          |
| ---------------- | ---------------------------------------------- |
| `Organization`   | The `Settings` global's `name` and `logo`      |
| `LocalBusiness`  | `name`, `address`, `phone`, `openingHours`     |
| `Person`         | `name`, `title`, `email`, `photo`              |
| `Article`        | `title`, `author`, `publishedAt`, `cover`      |
| `Event`          | `name`, `startsAt`, `endsAt`, `location`       |
| `JobPosting`     | `title`, `description`, `location`, `postedAt` |
| `BreadcrumbList` | The page's place in the site                   |

A field it misses, or a fact the item does not hold, goes in `with`:

```tsx
<JsonLd
    type="LocalBusiness"
    of={office}
    with={{
        priceRange: '££',
    }}
/>
```

There is no `FAQPage`: Google stopped showing it in 2026.

## Redirects

A `redirects` collection, served by `nextAdapter()` at request time. Nothing redeploys.

| Field       | What it is                                            |
| ----------- | ----------------------------------------------------- |
| `from`      | The old path, unique per site                         |
| `to`        | A path, a URL, or a page or item that follows renames |
| `permanent` | `308`, or `307` for a campaign address                |

1. An article publishes with a new slug.
2. The old address redirects to it.
3. Earlier redirects to the article follow.
4. A redirect from the new address is removed.

Rename-made redirects are read-only. `/offices` and `/offices/` are two addresses, as [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) says. `GET /content/redirects` lists them for anything that is not Next.

## The sitemap

```ts title="src/app/sitemap.ts"
export default async function sitemap() {
    return sitemapOf(kizuna.content, {
        siteUrl: 'https://example.co.uk',
    });
}
```

One sitemap per language under an index, `lastmod` from the last publish, `noindex` pages left out.

## Languages

The page's `metadata` writes `alternates.languages`: an absolute address per published language, the page's own, and `x-default`. Region tags are [BCP 47](https://www.rfc-editor.org/rfc/rfc5646), `en-GB`. An unpublished language is not listed.

## Images

`ImageSchema` requires alt text. The media record keeps width and height, and `?w=` serves each size for `srcset`.

## AI search

Answer engines cite pages the way search engines rank them: indexed, plain, with an author and a date. The CMS makes those true on every page:

- **Visible dates and a named author.** An article shows `datePublished` and `dateModified` on the page and in its structured data, and the author is a person with a page of their own.
- **Plain facts in typed fields.** An office's address, hours and phone number are fields, so the page states them rather than burying them in a paragraph.
- **The crawlers that cite are let in.** The site's `robots.txt` names the answer engines' search crawlers, `OAI-SearchBot`, `Claude-SearchBot` and `PerplexityBot`, and `robots.ts` from the CMS writes the groups. Whether the training crawlers, `GPTBot` and `ClaudeBot`, may read the site is a site setting, off by default.
- **Each publish tells the engines that read pings.** Bing, DuckDuckGo and the engines built on them learn of a change through [IndexNow](https://www.indexnow.org) the moment a page publishes or an address changes. Google does not take pings, and reads the sitemap.

Two things sound like they should matter and the evidence says they do not. Structured data on a page does not make it cited more often, in a matched study of nearly two thousand pages. A `llms.txt` file is fetched on three percent of the sites that have one, and Google does not read it. The CMS writes neither for that reason, and what moves citations most, by the same studies, is the site being mentioned elsewhere, which is marketing's work rather than the CMS's.

Search Console reports AI results under "Web", and Bing Webmaster Tools has a report of its own for Copilot citations.

## Moving from another platform

A move keeps its search standing when every old address answers. Export the old platform's redirect table and crawl the live site, including blog posts, PDFs and uploaded files, and import the map:

```sh
kizuna cms import-redirects old-site.csv
```

Each old address answers with a `301` straight to its new page, never to the front page, and never through another redirect. Imported articles keep their original `datePublished`. Keep the old domain pointing at the new site for a year, since links to it are still out there.

HubSpot keeps its forms inside HubSpot, and they embed on the new site as they are, so lead capture carries on while the site moves. Its uploaded files, under `/hubfs/`, cannot be redirected from HubSpot's side, so copy them into the media library and map their addresses with the rest.
