A search engine reads the title, the dates, the author and the address off a page, and the CMS writes those from the typed fields. A person writes the search title and the description.

## A page owns its search result

A page says what search engines see of it, beside its fields, typed from them. It gives its own words and nothing of the site's:

```ts title="src/app/blog/[slug]/content.ts"
export default definePage({
    name: 'articlePage',
    collection: Articles,
    metadata: {
        title: ({ content }) => content.title,
        description: ({ content }) => content.summary,
        image: ({ content }) => content.cover,
        type: 'Article',
    },
});
```

| Field         | What it is                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------- |
| `title`       | The page's own words in the result. 30 to 60 characters show in full, suffix included         |
| `description` | One or two sentences under it. 70 to 160 characters show in full                              |
| `image`       | The image a shared link shows. Without one, the page's first image                            |
| `type`        | The [structured data](#structured-data) the page carries, `Article`, `LocalBusiness`, `Event` |
| `noindex`     | Keep the page out of search results, like a campaign page only reached by its link            |
| `suffix`      | `false` for a page whose title stands alone, like the front page                              |

`content` is the page's fields, and a field the function names that the page does not have fails to compile. A page without `metadata` uses its heading, its first paragraph and its first image.

The front page is the one page whose title is the site's, so it stands alone:

```ts title="src/app/(front-page)/content.ts"
export default definePage({
    name: 'frontPage',
    fields: [
        {
            name: 'tagline',
            schema: z.string().max(80),
        },
    ],
    metadata: {
        title: ({ content, site }) => `${site.name}: ${content.tagline}`,
        suffix: false,
    },
});
```

`site` is the `Site` global's published fields, so the front page reads the site's name without the join adding it again. Any page can do the same when its title is a whole of its own, like a campaign page named after the campaign.

### The site joins them

The site's name and the separator live in one place, on `cms()`, and every page's title goes through it:

```ts title="kizuna.config.ts"
content: cms({
    db,
    pages,
    globals: [Site],
    metadata: {
        title: ({ title, site }) => `${title} | ${site.name}`,
    },
}),
```

`title` is what the page gave, and `site` is the `Site` global's published fields, so editors rename the site without a deploy and changing `|` to `–` is this one line. A section that wants a suffix of its own, like the blog, gets it here too, from the page's name, so the separator still lives in one place:

```ts
title: ({ title, site, page }) => (page === 'articlePage' ? `${title} | ${site.name} Blog` : `${title} | ${site.name}`),
```

With [several sites](/docs/cms/sites), each site has its own `Site` global, and a site sets its own `metadata` only to differ from what is on `cms()`.

### What a person writes

The functions give every page a result the moment it is published. `MetadataSchema` is the field for the pages a person wants to write by hand:

```ts
{
    name: 'metadata',
    label: 'Search result',
    schema: MetadataSchema,
},
```

The editor shows it as a search result, with the function's title and description filled in as placeholders and each length measured against what a result shows in full, suffix included. What a person types wins over the function for that page, and goes through the site's join like any other title.

## Rendering

A page's metadata is one export. The CMS knows the page's `metadata`, the site's join, the Open Graph and Twitter tags that follow from them, the canonical address and the page's other languages:

```tsx title="src/app/blog/[slug]/page.tsx"
export const generateMetadata = kizuna.content.pages.articlePage.metadata;
```

It reads the route's `params` the way `get` does, and returns the title as `absolute`, so Next's own `title.template` never adds a second suffix. A page that adds something of its own spreads it:

```tsx title="src/app/blog/[slug]/page.tsx"
export async function generateMetadata(props: PageProps): Promise<Metadata> {
    return {
        ...(await kizuna.content.pages.articlePage.metadata(props)),
        openGraph: {
            type: 'article',
        },
    };
}
```

Social cards often want the page's words alone, so `og.title` on `cms()` is a join of its own, `({ title }) => title`, and otherwise the Open Graph title follows the page's.

## Structured data

A search engine shows an office's opening hours, an article's date and an event's venue when the page says what they are in [schema.org](https://schema.org) terms. The CMS writes that from the typed content, so an office that moves updates its structured data with the rest:

```tsx title="src/app/offices/[id]/page.tsx"
import { JsonLd } from '@kizunajs/cms/metadata';

export default async function OfficePage({ params }: { params: Promise<{ id: string }> }) {
    const { id } = await params;
    const office = await kizuna.content.collections.offices.get({
        id,
    });

    return (
        <main>
            <JsonLd type="LocalBusiness" of={office} />
            <h1>{office.name}</h1>
        </main>
    );
}
```

`JsonLd` maps the fields a type expects from the fields the item has, `name`, `address`, `telephone`, `openingHours`, and takes any it cannot find by name:

| Type             | From                                           |
| ---------------- | ---------------------------------------------- |
| `Organization`   | The site global: name, logo, address, `sameAs` |
| `LocalBusiness`  | An office                                      |
| `Person`         | An employee, with the page that is theirs      |
| `Article`        | An article: headline, dates, author, images    |
| `Event`          | An event: dates, venue, offers                 |
| `JobPosting`     | A vacancy                                      |
| `BreadcrumbList` | The page's place in the site                   |

`Organization` belongs on the front page and the about page, and nowhere else. A `FAQPage` is not in the list: Google stopped showing FAQ and how-to rich results in 2026, so a list of questions is better as visible content on the page.

## Addresses

An address is for life. The CMS keeps a `redirects` collection, listed in the editor with the rest, and `nextAdapter()` answers every address in it at request time, so a new redirect works the moment it publishes and nothing redeploys.

A redirect is an address and where it goes:

| Field       | What it is                                                                                                  |
| ----------- | ----------------------------------------------------------------------------------------------------------- |
| `from`      | The old address, a path on this site, unique                                                                |
| `to`        | A path on this site, a full URL, or a page or item, which keeps working when that one is renamed again      |
| `permanent` | `true` answers `308`, for a page that moved. `false` answers `307`, for a campaign address that will change |

An editor adds one by hand for a campaign address or a page that moved to another site, and the agent adds them when asked. The rest the CMS writes itself:

- **A rename makes a redirect.** When an article's published slug changes, the old address redirects to the article. A draft with a new slug makes nothing until it publishes, since the old address is still the live one.
- **Chains collapse.** When the article is renamed again, every redirect that points at it follows to the new address, so no visitor goes through two.
- **Loops cannot form.** A redirect from the new address is removed the moment that address goes live, so renaming a page back to an earlier slug just works.
- **A written redirect is read-only.** The ones a rename made show in the editor with the rename that made them, and deleting the article deletes them.

A path includes its language, `/nb/kontor` and `/en/offices` are two addresses, so a redirect never needs translating. With [several sites](/docs/cms/sites), each site has its own redirects, since each has its own domain.

Paths match exactly, as [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) says they do, so `/offices` and `/offices/` are two addresses. Pick one shape for the site and the CMS writes every address in it.

Outside Next, `GET /content/redirects` lists the published redirects for whatever serves the site, and the list is cached and refreshed like any other content.

## The sitemap

The site's `sitemap.ts` asks the CMS for every published page, with `lastmod` from the day it was last published, which is the one thing a search engine reads from a sitemap:

```ts title="src/app/sitemap.ts"
import { sitemapOf } from '@kizunajs/cms/metadata';

export default async function sitemap() {
    return sitemapOf(kizuna.content, {
        siteUrl: 'https://example.co.uk',
    });
}
```

A site in several languages gets one sitemap per language under an index, and a page marked `noindex` is left out.

## Languages

A page that exists in Norwegian and English tells search engines so, and each language points at the others. The CMS knows every published translation's address, so a page's alternates come from it:

```tsx title="src/app/[locale]/blog/[slug]/page.tsx"
export const generateMetadata = kizuna.content.pages.articlePage.metadata;
```

The page's `metadata` writes `alternates.languages` with an absolute address per published language and the page's own, which search engines require of each other, and `x-default` for the main site when there is one. Region tags follow [BCP 47](https://www.rfc-editor.org/rfc/rfc5646), `en-GB` for the UK, and a language that is not published is not listed. A page that falls back to another language's content is listed under the language it shows, so two addresses never claim the same words.

## Images

Alt text is the one thing a search engine reads from an image. `ImageSchema` requires it per use, and the media record keeps the width and height, so a page renders an image at the size it shows with no layout shift. `?w=` on the image route serves each size, which the page uses for `srcset`.
