```ts title="src/cms/content.ts"
import { z } from 'zod';
import { Kizuna } from 'kizunajs';
import { defineCollection } from '@kizunajs/cms';
import { ImageSchema } from '@kizunajs/cms/schemas';

export const EmployeeId = Kizuna.brand('EmployeeId', z.string());

export const Employees = defineCollection({
    name: 'employees',
    id: EmployeeId,
    fields: [
        {
            name: 'name',
            schema: z.string().min(1).max(60),
        },
        {
            name: 'department',
            schema: z.enum(['design', 'engineering', 'sales', 'support']),
            options: {
                design: 'Design',
                engineering: 'Engineering',
                sales: 'Sales',
                support: 'Support',
            },
        },
        {
            name: 'photo',
            schema: ImageSchema.optional(),
        },
    ],
    indexes: ['department'],
});
```

An item is a draft until published. `indexes` are the fields a list filters and sorts by, the editors' list in the [admin](/docs/cms/editing/admin#lists) and its [route](/docs/cms/editing/agents#listing-items) included. `columns` names more fields that list shows beside each item's title, without an index, so they show and never sort.

## Holding an item

```ts title="src/app/contact/content.ts"
{
    name: 'contactPerson',
    schema: Employees.id,
},
```

```tsx title="src/app/contact/page.tsx"
const content = await kizuna.content.pages.contactPage.get();
const contactPerson = await kizuna.content.collections.employees.get({
    id: content.contactPerson,
});
```

`z.array(Employees.id)` reads with `getMany({ ids })`, in the stored order. A read returns ids and never follows them, so there is no `depth`.

## The other direction

Employees hold an office's id, so the office page lists them:

```tsx title="src/app/offices/[id]/page.tsx"
const { items } = await kizuna.content.collections.employees.list({
    where: {
        office: id,
    },
});
```

The CMS records every id an item holds as it saves, so this needs no index and nothing is stored on the office.

## Items in an order

The team page lists people in the order an editor sets. `orderable` gives a collection that order:

```ts title="src/cms/content.ts"
export const Employees = defineCollection({
    name: 'employees',
    id: EmployeeId,
    orderable: true,
    fields: employeeFields,
    indexes: ['office'],
});
```

Editors drag the rows of its [list](/docs/cms/editing/admin#lists) into place, and `list()` returns the items in that order:

```tsx title="src/app/offices/[id]/page.tsx"
const { items } = await kizuna.content.collections.employees.list({
    where: {
        office: id,
    },
});
```

The collection has one order, and a filter keeps it, so the London page lists London's people in the order they have among everyone. Filtered to one office, the admin's list shows that office's people in the same order, and a drag there orders them among themselves.

A new item goes last. `orderBy` still sorts by any field of `indexes`, and leaving it out reads the order.

A move is a change to the item. The item reads Changed until it is published, the site keeps the old order until then, and a review covers it like any other change. Draft mode shows the order the drafts give.

Each item keeps its place as a short key that sorts between its neighbours, stored with its draft and its published copy, so moving one employee changes that employee alone. A reader never sees the key. Items saved before the collection said `orderable` have no place yet, and come last until the first move, which gives each of them the place it showed in.

#### Moving items from your own app

The [editing list](/docs/cms/editing/agents#listing-items) gives each item its `place`, and `PUT /editing/collections/employees/items/:id/place` moves one, beside another with `after` or `before`, or first or last with `at`. The route makes the new key and answers with it. To show a move before the answer arrives, make the same key in the browser and sort by it:

```ts
import { keyBetween } from '@kizunajs/cms/keys';

const place = keyBetween(above?.place, below?.place);
```

`@kizunajs/cms/keys` imports nothing, so it runs in any browser. The Swift and Kotlin clients emit `FractionalKey` for the same, `FractionalKey.between(above, below)`, once the API holds a place.

## Trees

A shop's tags nest: Workshop sits under Lighting, and Brushed brass under Brass under Materials. A collection whose items point at one of their own is a tree, and `tree` names the field that points up:

```ts title="src/cms/content.ts"
export const TagId = Kizuna.brand('TagId', z.string());

export const Tags = defineCollection({
    name: 'tags',
    id: TagId,
    group: 'Content',
    tree: 'parent',
    fields: [
        {
            name: 'name',
            schema: z.string().max(40),
        },
        {
            name: 'parent',
            schema: TagId.optional(),
            position: 'sidebar',
        },
    ],
});
```

A tag without a `parent` is at the top. An article holds its tags as it holds any item:

```ts title="src/cms/content.ts"
{
    name: 'tags',
    schema: z.array(Tags.id),
    position: 'sidebar',
},
```

Wherever a tag appears, editors and the model see it by its path, like "Lighting / Workshop". In the [admin](/docs/cms/editing/admin):

- The tags list shows the tree, and dragging a row onto another tag sets its `parent` in a draft.
- The article's picker shows the tree too, so an editor finds Workshop by opening Lighting.
- A filter on a tag can include every tag under it, so "Tags is within Lighting" finds an article tagged Workshop.

A save that would put a tag under itself, or under one of its own, is refused. Pages need no `tree`, since each already sits beside its route.

### A menu

A site's menu is a tree whose items keep an order, and renders two levels:

```ts title="src/cms/content.ts"
export const MenuItemId = Kizuna.brand('MenuItemId', z.string());

export const MenuItems = defineCollection({
    name: 'menuItems',
    id: MenuItemId,
    tree: {
        field: 'parent',
        depth: 2,
    },
    orderable: true,
    fields: [
        {
            name: 'label',
            schema: z.string().max(40),
        },
        {
            name: 'link',
            schema: z.string().max(200),
        },
        {
            name: 'parent',
            schema: MenuItemId.optional(),
            position: 'sidebar',
        },
    ],
});
```

`depth` counts levels, the top as one, so an item may sit under a top item and nothing may sit under that. A move or a save that would go deeper is refused. With `orderable`, siblings keep the order editors give them, and without it they sort by title, as tags do.

`list()` returns the items in their order, each with its `parent`. `Map.groupBy` keeps that order within each group, so the menu is two lookups:

```tsx title="src/components/site-menu.tsx"
const { items } = await kizuna.content.collections.menuItems.list();
const under = Map.groupBy(items, (item) => item.parent ?? null);

return (
    <ul>
        {(under.get(null) ?? []).map((item) => (
            <li key={item.id}>
                <a href={item.link}>{item.label}</a>
                <ul>
                    {(under.get(item.id) ?? []).map((child) => (
                        <li key={child.id}>
                            <a href={child.link}>{child.label}</a>
                        </li>
                    ))}
                </ul>
            </li>
        ))}
    </ul>
);
```

### Moving and deleting a parent

An item takes everything under it wherever it goes, since each of those still points at it.

An item shows on the site once everything above it is published. Unpublishing About takes Careers and Contact off the menu with it, and a new parent with new items under it can be published in any order.

Deleting an item moves everything under it to the [trash](/docs/cms/editing/admin#trash) with it, and restoring the item brings them back together. The admin names what goes with it before it asks, and the model's delete tool asks the person first, as every delete does.

## Actions

An action is an entry in an item's `…` menu in the admin, and its handler is your code. A newsletter is content, so it is a collection, and sending it is an action:

```ts title="src/cms/content.ts"
export const Newsletters = defineCollection({
    name: 'newsletters',
    id: NewsletterId,
    fields: [
        {
            name: 'subject',
            schema: z.string().max(80),
        },
        {
            name: 'body',
            schema: RichTextSchema,
        },
    ],
    actions: {
        send: {
            auth: {
                roles: 'admin',
            },
            confirm: 'Send to everyone on the weekly list?',
            handler: async ({ item, plugins }) => {
                await plugins.resend.sendBroadcast({
                    list: 'weekly',
                    subject: item.subject,
                    html: renderNewsletter(item.body, '{{{FIRST_NAME|there}}}'),
                });
            },
        },
    },
});
```

Editors write the newsletter as a draft, ask for a review, and an admin picks Send. `item` is the published item. Actions take the same options as a [view's](/docs/cms/views#actions).

## Live Preview

An article has a page of its own, so the admin's **Live Preview** opens it there. An employee only appears on other pages, so its collection names the page to show it on:

```ts title="src/cms/content.ts"
export const Employees = defineCollection({
    name: 'employees',
    id: EmployeeId,
    preview: {
        url: () => '/team',
    },
    fields: [
        // ...
    ],
});
```

The team page lists employees with `list()`, which includes drafts in draft mode, so the editor sees the employee they are changing among the rest, updating as they type.

When the card appears in several places, a page of its own can show it in each of them. `url` receives the item, so the page can take its id:

```ts title="src/cms/content.ts"
preview: {
    url: ({ item }) => `/preview/employees/${item.id}`,
},
```

```tsx title="src/app/preview/employees/[id]/page.tsx"
import kizuna from '@kizuna-config';
import { EmployeeCard } from '../../../../components/employee-card';

export default async function EmployeePreview({ params }: { params: Promise<{ id: string }> }) {
    const employee = await kizuna.content.collections.employees.get({
        id: (await params).id,
    });

    return (
        <>
            <EmployeeCard employee={employee} />
            <EmployeeCard employee={employee} variant="compact" />
        </>
    );
}
```

The page renders through your own components, so the preview matches the site. In draft mode `get` reads the draft, and outside it the published item, as any page does.

`item` is the draft as it stands: the id, and the fields saved so far. A new item may not have them all yet, so `url` should work from the id alone. `url` returns a path on the site, which opens in [draft mode](/docs/cms/next#draft-mode).

A collection without `preview` opens its items on their own page when one [shows the collection](/docs/cms/pages#pages-that-show-a-collection), and otherwise on the first page that holds them. An item no page shows opens without a Live Preview.

## Collection or your own table

Would you keep the record if the website did not exist?

|            | Collection                            | Your table |
| ---------- | ------------------------------------- | ---------- |
| Examples   | Articles, testimonials, the team page |            |
| Written by | Editors, as drafts                    |            |
| Published  | Everything, once published            |            |
| On a page  | By id                                 |            |

A record in your own table can still be changed in the editor, through a [view](/docs/cms/views).

#### Moving between them

Both use the same `EmployeeId`, so pages keep working.

1. `kizuna cms export employees --out employees.json`
2. Insert them into your table, ids included, and serve a route.
3. Replace the collection with a relationship of the same name and id.
4. `kizuna cms orphans` lists the stored items to remove.

The other way, `kizuna cms import employees employees.json` creates drafts for an editor to publish.
