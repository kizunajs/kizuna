Sanity keeps content in its own cloud, the content lake, queried with GROQ, and the editor is a Studio you configure and host.

## The same page, both ways

An article page that shows the author's name.

<SideBySide>

```ts title="Kizuna: src/app/blog/[slug]/content.ts"
export default definePage({
    name: 'articlePage',
    collection: Articles,
});
```

```ts title="Sanity: schemaTypes/article.ts"
export const article = defineType({
    name: 'article',
    type: 'document',
    fields: [
        defineField({
            name: 'title',
            type: 'string',
        }),
        defineField({
            name: 'author',
            type: 'reference',
            to: [{ type: 'employee' }],
        }),
    ],
});
```

```tsx title="Kizuna: src/app/blog/[slug]/page.tsx"
const article = await kizuna.content.pages.articlePage.get(await params);
const author = await kizuna.content.collections.employees.get({
    id: article.author,
});
```

```tsx title="Sanity: src/app/blog/[slug]/page.tsx"
const article = await client.fetch(
    `*[_type == "article" && slug.current == $slug][0]{
        title,
        author->{ name }
    }`,
    { slug }
);
```

</SideBySide>

Both store Portable Text and both have a typed read. In Kizuna the page is declared beside its route and the content is in your database. In Sanity the page writes a query against a hosted store.

## Pick Sanity when

- You want a hosted content store and a real query language.
- The Studio's visual editing is what editors want.
- Content has no API of its own to share types with.
- Per-seat pricing fits the team.

## Pick Kizuna when

- Content belongs in the same database and the same types as the app.
- Editors are happy in their chat and on the page.
- Several sites share content and "where is this used" has to work across them.
- You would rather not pay per seat.
