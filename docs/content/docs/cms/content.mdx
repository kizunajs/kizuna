---

A page is a list of fields beside its route. A block is a set of fields several pages share. A global is content every page shows, and a collection holds many items of one shape, like articles. Each field is a name, a Zod schema, and who may edit it.

## Fields

```ts
{
    name: 'subheading',
    schema: z.string().max(200).describe('One sentence under the heading.'),
    auth: {
        roles: 'admin',
    },
},
```

| Option        | What it is                                                                                      |
| ------------- | ----------------------------------------------------------------------------------------------- |
| `name`        | The key the value is stored under. An identifier, since fields form paths like `hero.heading`.  |
| `label`       | What editors see the field called. Without one, they see its `name`.                            |
| `schema`      | Any Zod schema. Its limits hold in the API, the tools and the inline editor alike.              |
| `description` | Guidance under the input, for editors and the agent. Overrides the schema's `.describe()` here. |
| `auth`        | Who may write the field, in a route's own words: `roles`, or `requires` for permissions.        |
| `readOnly`    | Visible to editors and the agent, writable by nobody.                                           |
| `options`     | For an enum, the label editors see for each value: `{ design: 'Design' }`.                      |

A field listed twice fails to compile, and a role the editor identity does not declare fails when the config assembles.

## Blocks

A block is a set of fields you use wherever it belongs. Its rules and descriptions travel with it:

```ts title="src/cms/blocks.ts"
import { z } from 'zod';
import { defineBlock } from '@kizunajs/cms';
import { ImageSchema } from '@kizunajs/cms/schemas';
import { CtaSchema, HeadingSchema } from './schemas';

export const HeroBlockSchema = defineBlock({
    name: 'hero',
    fields: [
        {
            name: 'heading',
            schema: HeadingSchema,
        },
        {
            name: 'subheading',
            schema: z.string().max(200),
        },
        {
            name: 'image',
            schema: ImageSchema,
        },
        {
            name: 'cta',
            schema: CtaSchema,
        },
    ],
});
```

`defineBlock()` returns a Zod object schema, and `Output<T>` is that schema with images resolved, so the component is typed from the block:

```tsx title="src/components/Hero.tsx"
import type { Output } from '@kizunajs/cms';
import type { HeroBlockSchema } from '../cms/blocks';

export function Hero(props: Output<typeof HeroBlockSchema>) {
    return (
        <section>
            <img src={props.image.url} alt={props.image.alt} width={props.image.width} height={props.image.height} />
            <h1>{props.heading}</h1>
        </section>
    );
}
```

## Pages

```ts title="src/app/(front-page)/content.ts"
export default definePage({
    name: 'frontPage',
    fields: [
        {
            name: 'heading',
            schema: z.string().max(60),
        },
        {
            name: 'intro',
            label: 'Introduction',
            schema: z.string().max(400),
        },
    ],
});
```

`name` is how the page is read, `kizuna.content.pages.frontPage`, and how tools address it. Write it in camelCase with a `Page` suffix, unique across the site, and as a literal so discovery can read it.

Content is stored under the page's name, so moving the route's folder keeps it. A new name starts the page afresh, and the old content waits, listed by [`kizuna cms orphans`](/docs/cms/cli#kizuna-cms-orphans), until you move it:

```sh
kizuna cms rename-page pricingPage plansPage
```

## Globals

Content every page shows, like a footer or the contact details, is a global. One copy serves the whole site:

```ts title="src/cms/content.ts"
import { z } from 'zod';
import { defineGlobal } from '@kizunajs/cms';

export const Site = defineGlobal({
    name: 'site',
    fields: [
        {
            name: 'footerText',
            schema: z.string().min(1).max(160),
        },
        {
            name: 'contactEmail',
            schema: z.email(),
        },
    ],
});
```

## Collections

A collection holds many items of one shape, like the people on a team. Its items get an id type of their own, so a page can point at them the way it points at products:

```ts title="src/cms/content.ts"
import { z } from 'zod';
import { Kizuna } from 'kizunajs';
import { defineCollection } from '@kizunajs/cms';
import { ImageSchema } from '@kizunajs/cms/schemas';

export const EmployeeId = Kizuna.brand('EmployeeId', z.string());

export const Employees = defineCollection({
    name: 'employees',
    id: EmployeeId,
    fields: [
        {
            name: 'name',
            schema: z.string().min(1).max(60),
        },
        {
            name: 'department',
            schema: z.enum(['design', 'engineering', 'sales', 'support']),
            options: {
                design: 'Design',
                engineering: 'Engineering',
                sales: 'Sales',
                support: 'Support',
            },
        },
        {
            name: 'photo',
            schema: ImageSchema.optional(),
        },
        {
            name: 'order',
            schema: z.int().min(0).default(0),
        },
    ],
    indexes: ['department', 'order'],
});
```

An item starts as a draft and publishes like a page. `indexes` names the fields a list may filter and sort by, and `kizuna cms migrate` writes an index for each.

A page holds one item by its id:

```ts title="src/app/contact/content.ts"
{
    name: 'contactPerson',
    label: 'Contact person',
    schema: Employees.id,
},
```

and reads that one item, without listing the rest:

```tsx title="src/app/contact/page.tsx"
const content = await kizuna.content.pages.contactPage.get();
const contactPerson = await kizuna.content.collections.employees.get({
    id: content.contactPerson,
});
```

`get` reads one item and caches it on its own. A field that holds several, `z.array(Employees.id)`, reads them with `getMany({ ids })` in the order the page holds them.

Hand globals and collections to `cms()` beside the pages. `group` on either sorts it under a heading in the content overview:

```ts title="kizuna.config.ts"
content: cms({
    db,
    pages,
    globals: [Site],
    collections: [Employees],
    auth: {
        identity: 'editor',
    },
}),
```

## Collection or your own table

One question decides it: would you keep this record if the website did not exist?

- **No.** It is content, and it goes in a collection: articles, testimonials, FAQs, the people on a team page when no other system lists them. Content waits as a draft until someone publishes it, and everything published is public.
- **Yes.** It is a record your business keeps, and it goes in a table of yours with routes: products, orders, users, employees in an HR system. Customers, syncs and your code write to it, and your handlers run on every change.

A page holds both. It holds a record of yours by id, through a [relationship](#relationships), so you never copy one into a collection to put it on a page.

## Pages that show a collection

A blog post lives in a collection, and its route decides where each one is shown. A `content.ts` at a dynamic route names the collection instead of fields:

```ts title="src/app/blog/[slug]/content.ts"
import { definePage } from '@kizunajs/cms';
import { Articles } from '../../../cms/content';

export default definePage({
    name: 'articlePage',
    collection: Articles,
});
```

Each route param reads the item field it names, so `[slug]` reads `slug`. That field is text, indexed and unique, since it is the address. Editors create articles as items of the collection, and the preview opens each one at its address.

## Rich text

`RichTextSchema` is a field for formatted text, like an article body:

```ts
import { RichTextSchema } from '@kizunajs/cms/schemas';

{
    name: 'body',
    schema: RichTextSchema,
},
```

It stores [Portable Text](https://www.portabletext.org), structured JSON that never holds HTML: paragraphs, three levels of heading, quotes, lists, bold, italic, code, underline, links and images. Links go to `https://`, `http://`, `mailto:`, `tel:`, a path on the site or an `#anchor`, so a `javascript:` link fails the schema.

## Images

`ImageSchema` stores the media id with this use's alt text, crop and focal point, so one photo can be cropped differently on every page:

```json
{
    "id": "med_3f2a9c1e8b7d4a5f6c0e1d2b",
    "alt": "Tulips in the morning",
    "crop": { "x": 0.1, "y": 0, "width": 0.8, "height": 1 },
    "focalPoint": { "x": 0.5, "y": 0.3 }
}
```

The page receives `{ id, url, alt, width, height }`, where `url` renders that crop. Editors upload in the preview. Where the files are stored is set up on [the CMS API](/docs/cms/api#images).

## Relationships

A page can hold things that live outside the CMS: products in your own API, or in a service like Stripe. The page holds their ids and fetches whatever it shows of them itself, so the CMS never reads a product for a visitor. What the CMS needs is the list an editor picks from, and a relationship gives it that list.

### From your own API

```ts title="src/cms/relationships.ts"
import { defineRelationship } from '@kizunajs/cms';
import { ProductId } from '../models';
import { apiClient } from '../lib/api-client';

export const Products = defineRelationship({
    name: 'products',
    id: ProductId,
    options: async ({ query, ids, headers }) => {
        const result = await apiClient.products.listProductOptions({
            query: {
                q: query,
                ids,
            },
            headers,
        });
        return result.status === 200 ? result.body.options : [];
    },
});
```

`options` feeds the picker and nothing else: an id, a label and an optional image for each product. It gets `query` when an editor searches, and `ids` to name the products a field already holds. It runs as the editor, with their sign-in in `headers`, so your route decides what they may see. `ProductId` is the same type on your routes and in the generated client, so the ids pass straight through.

Point it at a route that reads only those three, so the picker fetches no more than it shows:

```ts title="src/routes/products.ts"
listProductOptions: k
    .route({
        method: 'GET',
        path: '/product-options',
        auth: 'staff',
        query: z.object({
            q: z.string().optional(),
            ids: z.array(ProductId).optional(),
        }),
        responses: {
            200: z.object({
                options: z.array(
                    z.object({
                        id: ProductId,
                        label: z.string(),
                        image: z.url().optional(),
                    })
                ),
            }),
        },
    })
    .handler(async ({ query }) => {
        const options = await db
            .select({
                id: products.id,
                label: products.name,
                image: products.imageUrl,
            })
            .from(products)
            .where(query.ids === undefined ? ilike(products.name, `%${query.q ?? ''}%`) : inArray(products.id, query.ids))
            .limit(20);

        return {
            status: 200,
            body: {
                options,
            },
        };
    }),
```

### From another service

Ids from another service get a type of their own, named after it, so a Stripe product id never passes for one of yours:

```ts title="src/cms/relationships.ts"
import Stripe from 'stripe';
import { z } from 'zod';
import { Kizuna } from 'kizunajs';
import { defineRelationship } from '@kizunajs/cms';

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!);

export const StripeProductId = Kizuna.brand('StripeProductId', z.string());

const findProducts = async (query: string | undefined, ids: string[] | undefined) => {
    if (ids !== undefined) {
        return stripe.products.list({
            ids,
            limit: 100,
        });
    }
    if (query === undefined || query === '') {
        return stripe.products.list({
            active: true,
            limit: 20,
        });
    }
    return stripe.products.search({
        query: `active:'true' AND name~'${query.replaceAll("'", "\\'")}'`,
        limit: 20,
    });
};

export const StripeProducts = defineRelationship({
    name: 'stripeProducts',
    id: StripeProductId,
    options: async ({ query, ids }) => {
        const found = await findProducts(query, ids);
        return found.data.map((product) => ({
            id: product.id,
            label: product.name,
            image: product.images[0],
        }));
    },
});
```

It calls Stripe with your secret key rather than the editor's sign-in, so it leaves `headers` alone.

### Holding them on a page

List each relationship on `cms()`, beside the collections:

```ts title="kizuna.config.ts"
content: cms({
    db,
    pages,
    collections: [Articles],
    relationships: [Products, StripeProducts],
    auth: {
        identity: 'editor',
    },
}),
```

A page field holds the ids:

```ts title="src/app/(front-page)/content.ts"
{
    name: 'featured',
    schema: z.array(Products.id).max(6),
    description: 'Shown in the grid, in this order.',
},
```

The CMS stores and returns ids. The page fetches what it shows, from whichever route and with whichever fields it needs:

```tsx title="src/app/(front-page)/page.tsx"
import { inStoredOrder } from '@kizunajs/cms/next';

export default async function FrontPage() {
    const content = await kizuna.content.pages.frontPage.get();
    const result = await apiClient.products.listProducts({
        query: {
            ids: content.featured,
        },
    });
    const featured = inStoredOrder(content.featured, result.status === 200 ? result.body.products : [], (product) => product.id);

    return <ProductGrid products={featured} />;
}
```

`inStoredOrder` keeps the order the editor chose and drops ids that found nothing, so a deleted product leaves the grid. When a product changes, call [`invalidate`](/docs/cms/api#talking-to-the-app) with the relationship's name, from your own route or from a Stripe webhook, and every page that holds it refreshes.

## Limits that keep the design

A page keeps its design because its fields refuse what would break it. Designers say what they want, and the schema holds it for the editor, the agent and the API alike:

| You want                                   | The schema says                      | The editor sees                          |
| ------------------------------------------ | ------------------------------------ | ---------------------------------------- |
| A short heading                            | `z.string().max(60)`                 | A counter that stops at 60 characters    |
| One of a few looks                         | `z.enum(['light', 'dark'])`          | A select                                 |
| Two to six products                        | `z.array(products.id).min(2).max(6)` | A sortable list that stops adding at six |
| A link that is https                       | `z.url({ protocol: /^https$/ })`     | A URL input that says https only         |
| An image with a crop and alt text          | `ImageSchema`                        | Upload, crop and alt text                |
| A field only the client's admin may change | `auth: { roles: 'admin' }`           | The field, greyed out                    |

A character limit keeps a heading short, and letters differ in width, so check the design with the longest heading the limit allows. `.describe()` is what the editor and the agent read under the input, so give the reason: `'Under 8 words. No full stop.'`

## Changing the shape

A new field says what stored content gets. Give it a `.default()`, or a `migrate` step keyed by the next version number:

```ts
migrate: {
    1: (document) => ({
        ...document,
        subheading: '',
    }),
},
```

Reads run the step in memory, and the document's next save stores the result, so migrating never publishes anything. [`kizuna diff`](/docs/breaking-changes#content) fails a pull request that adds a required field with neither. If one ships anyway, visitors see the newest earlier version that still passes, or nothing when none does, and [`kizuna cms check`](/docs/cms/cli#kizuna-cms-check) lists the page.

A rename is a removal and an addition, so write a step that moves the value. `richTextFromPlain` turns a text field into rich text:

```ts
migrate: {
    2: (document) => ({
        ...document,
        body: richTextFromPlain(String(document['body'] ?? '')),
    }),
},
```
