A site with only content needs one config. When the site has an app API too, like a shop's products and orders, give the CMS a config of its own, so editors and content tools never mix with the app's routes, clients and MCP tools:

```ts title="kizuna.cms.config.ts"
export default defineConfig({
    adapter: nextAdapter(),
    auth: {
        identities: {
            editor,
            app,
        },
    },
    content: cms({
        db,
        pages,
        auth: {
            identity: 'editor',
            invalidate: 'app',
        },
        apiPath: '/cms-api',
        signInPath: '/login',
    }),
});
```

Mount it at `apiPath`, in `src/app/cms-api/[...kizuna-cms]/route.ts`, and point `@kizuna-config` at `kizuna.cms.config.ts`, since that is the config pages read content from. Editors enter draft mode at `/cms-api/draft`.

## The routes

The CMS routes come in three groups, one for each kind of caller:

| Group        | Called by                | What it holds                                                                 |
| ------------ | ------------------------ | ----------------------------------------------------------------------------- |
| `content`    | Anyone                   | Published pages, globals, collection items and images                         |
| `editing`    | Editors and their agents | Drafts, publishing, versions, media, describe, where-used, search and preview |
| `invalidate` | The app                  | Refreshing the pages that show an id the app changed                          |

`content` is a REST API of everything editors publish, generated from your fields: `GET /cms-api/content/pages/frontPage`, `GET /cms-api/content/collections/employees`. A collection's list takes `select`, `?select=name,photo`, and answers with those fields and the id. Every collection also answers `GET /cms-api/content/collections/employees/options`, the id and label of each published item, searchable by `q` and looked up by `ids`, which is what a [relationship](/docs/cms/content#from-another-kizuna-api) in another CMS reads. The label is the item's first text field.

## A client for readers

A frontend, a phone or another repository reads content and nothing else. `groups` keeps a generated client to the groups it names:

```ts title="kizuna.cms.config.ts"
clients: [
    fetchClient({
        output: './src/lib/content-client.generated.ts',
        groups: ['content'],
    }),
],
```

```ts title="src/lib/front-page.ts"
const result = await contentClient.content.pages.frontPage();
```

`kizuna.content.pages.frontPage.get()` in process and `contentClient.content.pages.frontPage()` over HTTP read the same content by the same path. The Swift and Kotlin clients take `groups` the same way, and so does the OpenAPI document, for readers that generate their own:

```ts title="kizuna.cms.config.ts"
plugins: [
    openApiPlugin({
        info: {
            title: 'Content',
            version: '1.0.0',
        },
        groups: ['content'],
        docsPath: '/cms-api/docs',
    }),
],
```

A client without `groups` holds every route, which is what an app that edits content needs.

## Publishing a client

Another repository reads content through a client it installs, like the UK's booking app built by another team. Generate one for the site it serves: the UK's routes and the group's, and nothing of the other sites or the editing routes:

```ts title="packages/content/kizuna.cms.config.ts"
clients: [
    fetchClient({
        output: './packages/uk-content/src/index.ts',
        groups: ['content.sites.uk', 'content.globals', 'content.collections', 'content.media'],
    }),
],
```

The output is a package of its own, with a name and a version, published wherever your packages go, like npm or GitHub Packages:

```json title="packages/uk-content/package.json"
{
    "name": "@acme/uk-content",
    "version": "1.4.0",
    "type": "module",
    "exports": "./dist/index.js",
    "types": "./dist/index.d.ts",
    "files": ["dist"],
    "scripts": {
        "build": "tsc"
    }
}
```

The generated file imports nothing, so the package has no dependencies. The site installs the version it wants and calls the group's API:

```ts title="booking-app/src/lib/content.ts"
import { createClient } from '@acme/uk-content';

export const content = createClient({
    baseUrl: 'https://example.com/api',
});
```

The branded ids come with it, so an `OfficeId` is the same type in the client as in the CMS. A [site in another repository](/docs/cms/sites#a-site-in-another-repository) holds no pages here, so its client names the group's groups alone: `content.globals`, `content.collections` and `content.media`. Gate the group's releases with [`kizuna diff`](/docs/breaking-changes): a field removed or a type narrowed fails the pull request before a published client can break a site that installed it.

## What stays apart

- **Identities.** `editor` lives on the CMS config, so an app route that names it fails to compile. When a [relationship's](/docs/cms/content#relationships) `options` calls a route that is not public, the editor also needs an identity on the app API, since `options` runs as them.
- **MCP.** An editor's agent connects to `/cms-api/mcp` and sees content tools alone.
- **Clients and OpenAPI.** Each API generates its own. A mobile app gets the app client, and reads content through [a route on the app API](#content-in-the-app-api) or a [client of the content routes](#a-client-for-readers).
- **Shared ids.** Ids both sides use, like `ProductId`, live in a module both configs import.

## Talking to the app

When the app changes a product, it calls `invalidate` through the CMS client, and every page that shows the product refreshes. The route answers the identity `auth.invalidate` names, here `app`, an API key only the app's server holds:

```ts title="src/routes/products.ts"
.handler(async ({ params, body }) => {
    const product = await renameProduct(params.id, body.name);
    await cmsClient.invalidate({
        body: {
            relationship: 'products',
            id: params.id,
        },
    });

    return {
        status: 200,
        body: product,
    };
}),
```

## Content in the app API

A mobile app talks to the app API, and its news feed comes from the CMS. A route on the app API reads the CMS in process and answers in its own shape, so the Swift and Kotlin clients get the articles from the same client as the rest of the app.

The app imports the CMS config's reader:

```ts title="src/lib/content.ts"
import kizunaCms from '../../kizuna.cms.config';

export const content = kizunaCms.content;
```

A route lists the published articles and answers with what the app needs of them:

```ts title="src/routes/news.ts"
listNews: k
    .route({
        method: 'GET',
        path: '/news',
        auth: false,
        summary: 'List the latest news',
        responses: {
            200: z.object({
                articles: z.array(
                    z.object({
                        id: ArticleId,
                        title: z.string(),
                        imageUrl: z.url(),
                    })
                ),
            }),
        },
    })
    .handler(async () => {
        const { items } = await content.collections.articles.list({
            select: ['title', 'image'],
            limit: 20,
        });

        return {
            status: 200,
            body: {
                articles: items.map((article) => ({
                    id: article.id,
                    title: article.title,
                    imageUrl: article.image.url,
                })),
            },
        };
    }),
```

The reader returns published content alone, since the route has no draft mode. `select` reads the title and image of each article and leaves its body behind, and the items are typed to what it names. `ArticleId` is the collection's own id type, so a later route that takes one, like `getNewsArticle`, accepts the ids this one returned.

The phone needs a full URL, so set `media.publicPath` to one, `'https://example.com/cms-api/content/media'`, and every image's `url` starts with it. The phone asks for the size it shows by adding `w`, as [below](#image-sizes).

With [sites](/docs/cms/sites), the route reads the site the app belongs to, `content.sites.norway.collections.articles.list()`.

## Images

Files live in an S3 bucket, so any S3-compatible store works. Point the CMS at yours with environment variables:

| Variable                   | What it is                                                                          |
| -------------------------- | ----------------------------------------------------------------------------------- |
| `CMS_S3_BUCKET`            | The bucket                                                                          |
| `CMS_S3_ENDPOINT`          | The store's S3 endpoint for Supabase Storage, Cloudflare R2 or MinIO. Unset for AWS |
| `CMS_S3_REGION`            | `auto` for R2, your project's region for Supabase, the bucket's for AWS             |
| `CMS_S3_ACCESS_KEY_ID`     | Falls back to the SDK's own lookup                                                  |
| `CMS_S3_SECRET_ACCESS_KEY` | Falls back to the SDK's own lookup                                                  |

The same names go under `media` on `cms()`. The bucket can stay private: browsers upload through a presigned URL and read through `GET /content/media/:id/image`, which renders the crop and caches for a year. Without a bucket, development keeps files in memory and production refuses to start.

### Image sizes

An image's `url` renders the crop an editor chose. `w` and `h` render it at a size, up to 4096 pixels, and each size is cached on its own:

```text
/cms-api/content/media/med_3f2a9c1e8b7d4a5f6c0e1d2b/image?crop=0.1,0,0.8,1&w=800
```

With `w` alone the height follows the crop. With both, the image is cropped to fit around the focal point the editor set, so a square thumbnail keeps the face in it.

Uploads are checked by their bytes, never their name. SVG is refused, location metadata is stripped, and files over ten megabytes are refused unless `media.maxBytes` says otherwise.

## Sites

A group with a site per country runs one CMS. The group's content is written once and every site reads it, and each site adds content of its own. See [Sites](/docs/cms/sites).

## Deployment

Most projects mount both APIs in one Next.js app. A sensitive project can run the CMS API as an app of its own instead: the CMS client's `baseUrl` moves, and `revalidate` on `cms()` calls a route on the site that runs `revalidateTag`.

Either way the content stays in the app's database. Connect the CMS as a role that reaches only its tables, so a CMS bug cannot reach app data:

```sql
create role cms_editor login password '…';
grant select, insert, update, delete on cms_documents, cms_versions, cms_refs to cms_editor;
```

Each config generates on its own. The app imports the CMS client, so the CMS goes first:

```sh
kizuna generate --config kizuna.cms.config.ts
kizuna generate
```
