The CMS routes come in three groups:

| Group        | Called by                                 | What it holds                                     |
| ------------ | ----------------------------------------- | ------------------------------------------------- |
| `content`    | Anyone, or the identity `auth.read` names | Published pages, globals, items and images        |
| `editing`    | Editors and their agents                  | Drafts, publishing, versions, reviews, search     |
| `invalidate` | Your app, and your other deployments      | Refreshing an id, a global or a page that changed |

`GET /api/content/collections/employees` is the REST API, and every collection also serves `.../options`. Content routes are public, and `auth.read` on `cms()` makes every one of them require the identity it names. Image files at `/content/media/:id/image` stay public, since a browser loads them with no token.

With [several sites](/docs/cms/sites), every content route sits under its site, at `/content/sites/<site>/...`, and media stays at `/content/media`. `GET /api/content/sites/uk/collections/offices` answers with the shared offices and the UK's values in place, and `GET /api/content/sites/uk/collections/events` with the UK's events.

## A client for readers

```ts title="kizuna.config.ts"
clients: [
    fetchClient({
        output: './src/lib/content-client.generated.ts',
        groups: ['content'],
    }),
],
```

`contentClient.content.pages.frontPage()` over HTTP reads what `kizuna.content.pages.frontPage.get()` reads in process. Swift, Kotlin and OpenAPI take `groups` the same way.

## Publishing a client

Another repository, like a [partner's](/docs/cms/sites#partners), installs the client as a package. Generate it for the site it reads, and the client holds that site's routes, with the same paths as `kizuna.content` on that site:

```ts title="packages/content/kizuna.cms.config.ts"
fetchClient({
    output: '../uk-content/src/index.ts',
    groups: ['content.sites.uk'],
}),
fetchIds({
    output: '../uk-content/src/ids.ts',
    groups: ['content.sites.uk'],
}),
```

`fetchIds` writes the Zod brands the client names, like `OfficeId`, so the package has two entries: the client, and `./ids` with the brands, for the other repository's own schemas to hold your ids. Publish it where your packages go.

`kizuna diff` fails a change that would break a published client, judged by that client's `groups`, so a change to Norway never fails the UK's client. The snapshot records each brand's name, so renaming `EmployeeId` counts as breaking.

## Partners reading

A partner reads with that client and a token from OAuth client credentials, signing in as the identity `auth.read` names. It may read the sites its `reads` names and the shared content, and a read of another site answers `403`, naming the permission it lacks, like `content.sites.norway:read`. A token whose guard returns no `partner` reads every site. A read with a token answers with `Cache-Control: private`. [Partners](/docs/cms/sites#partners) shows the config, the sign-in and how a partner hears a publish.

## Content in the app API

A mobile app reads content through a route on your API, which reads the CMS in process:

```ts
.handler(async () => {
    const { items } = await content.collections.articles.list({
        select: ['title', 'image'],
        limit: 20,
    });
    return {
        status: 200,
        body: {
            articles: items,
        },
    };
}),
```

Set `media.publicPath` to a full URL so image URLs are absolute.

## Talking to the app

When your app changes a product, it calls `invalidate` through the CMS client, with the credential `auth.invalidate` names. The body says what changed:

| Body                         | Refreshes                                  |
| ---------------------------- | ------------------------------------------ |
| `{ brand: 'ProductId', id }` | The item, and every page that holds its id |
| `{ global: 'settings' }`     | A global                                   |
| `{ page: 'frontPage' }`      | A page                                     |

With [sites](/docs/cms/sites#publishing), the CMS calls the same route on each of your deployments after a publish, signed with the `kizuna-cms-signature` header in place of that credential.

## A config of its own

When the site has an app API too, give the CMS its own `kizuna.cms.config.ts`, mounted at its own `apiPath`, so editors, content tools and content clients never mix with the app's.
